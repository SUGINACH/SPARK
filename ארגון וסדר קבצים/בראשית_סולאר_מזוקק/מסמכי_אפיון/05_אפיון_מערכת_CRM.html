01

תפקיד ותפוקה

נקודת הכניסה הראשית של איש המכירות למערכת כולה — מסך הבית שממנו הוא בוחר לקוח, פותח עבורו טופס נתונים, מריץ חישוב, ומדפיס הצעת מחיר. זהו למעשה ה"CRM" הפנימי הקל של בראשית סולאר, בנוי על Google Apps Script עם Google Sheets כמסד נתונים.

מסמך זה, יחד עם מסמכים 01–04, מכסה את כל חמשת קבצי המערכת. זהו הקובץ ה"מחבר" ביניהם בפועל — ולכן גם המקום שבו מרוכזים רוב באגי האינטגרציה שתועדו.

03

ניתוב הדפים — doGet

מנגנון הניתוב המרכזי שמחבר את כל רכיבי המערכת יחד.

הקובץ פועל כ-Web App יחיד של Google Apps Script, עם פונקציית doGet(e) בצד השרת שמנתבת לפי פרמטר page ב-URL:

function doGet(e) {
  const page = e.parameter.page;
  if (page === 'form')       return renderPage('Form', e.parameter.clientId);
  if (page === 'calculator') return renderPage('Calculator');
  if (page === 'print')      return renderPage('PrintQuote');
  return renderPage('Index'); // ברירת מחדל: מסך הבית לאיש המכירות
}

04

הבעיה הקריטית: מנוע חישוב מוטמע כפול

מנוע חישוב פיננסי מוטמע (calcView), לא מסונכרן עם המחשבון החיצוני
הוחלט להסיר

בתוך Index.html קיים בלוק קוד מוטמע (מקור: שורות 203–291) שמכיל עותק עצמאי של מנוע החישוב הפיננסי — נפרד לגמרי מהמחשבון החיצוני המתועד במסמך 01. כשמתקנים באג או מעדכנים נוסחה במחשבון החיצוני, העותק המוטמע כאן לא מתעדכן אוטומטית, ונוצר מצב שבו שני חלקים של אותה מערכת נותנים תוצאות שונות לאותו לקוח.

ההחלטה שהתקבלה במסמך המאוחד: למחוק את calcView במלואו מ-Index.html, כך שה-CRM יישאר ממוקד בניהול לקוחות בלבד, ויסתמך אך ורק על המחשבון החיצוני האחד (מסמך 01) לכל חישוב פיננסי — מקור אמת יחיד.
05

גשר הנתונים השבור

מדוע localStorage נכשל בין דפי Google Apps Script.

localStorage לא עובד בין דפים ב-Google Apps Script
כשל ארכיטקטוני מתועד

השיטה המקורית להעברת תוצאות מהמחשבון בחזרה ל-Index הייתה: המחשבון שומר localStorage.setItem('transferredCalcData', ...) ונסגר; Index קורא מ-localStorage. זה נכשל באופן שיטתי — ב-Google Apps Script כל עמוד web-app מוגש בפועל מתת-דומיין googleusercontent.com נפרד (לעיתים בתוך iframe), ומדיניות המקור-הזהה (Same-Origin Policy) של הדפדפן חוסמת שיתוף localStorage בין שני "מקורות" שונים — גם אם שניהם טכנית "אותה מערכת". התוצאה בפועל: אובדן נתונים אקראי, תלוי-דפדפן, קשה לשחזור ולדיבוג.

06

הפתרון הארכיטקטוני שהוחלט

מעבר לפרמטרי URL + שמירה ישירה לשרת
הפתרון שהוחלט

במקום להסתמך על שיתוף מצב בצד הלקוח (Client-side), הארכיטקטורה החדשה:

  1. Index פותח את המחשבון עם נתוני הלקוח כפרמטרי URL — למשל ?clientId=123&roofArea=100 — במקום לצפות שהמחשבון "יזכור" משהו מוקדם יותר.
  2. בסיום החישוב, המחשבון שולח את התוצאה ישירות לשרת באמצעות google.script.run.saveCustomerData(payload) — לא דרך הדפדפן של הלקוח בכלל.
  3. Index (ו-PrintQuote) שולפים את התוצאה מהשרת/מ-Google Sheets לפי clientId, במקום לחכות שהיא "תעבור" מדף לדף.

הגישה הזו גם פותרת את בעיית מגבלת 5MB של localStorage שתועדה במסמך 01 (חלק 9) עבור מערכי צריכה שעתיים גדולים.

07

כפילות באיסוף נתוני צרכנים

Index אוסף נתוני צרכנים בצורה בסיסית, Form אוסף בעושר — יש לאחד כיוון
כפילות מתועדת

ל-Index.html יש יכולת בסיסית משלו להזין פרטי צרכן/לקוח, במקביל ליכולת העשירה הרבה יותר של Form.html (מסמך 04: מכשירים, מיקומים, שעות הפעלה). כאשר איש מכירות ממלא נתונים ישירות ב-Index ולא מפנה את הלקוח לטופס המלא, המחשבון מקבל תמונה חלקית בהרבה. כיוון מומלץ: להפוך את Index ל"ניתוב" בלבד — כל הזנת נתוני צריכה מפורטת מנותבת תמיד ל-Form.html, ו-Index משמש רק לניהול רשימת לקוחות וסטטוסים.

פעולות נדרשות

    בניית פונקציית השרת שמקבלת את תוצאות המחשבון ושומרת ב-Sheets לפי clientId, ומחליפה את מנגנון ה-localStorage.

    ניתוב מלא לטופס העשיר במקום קלט בסיסי ב-Index
