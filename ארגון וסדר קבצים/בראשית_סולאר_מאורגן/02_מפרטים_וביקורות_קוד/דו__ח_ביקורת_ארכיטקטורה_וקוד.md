**מסמך אדריכלות מורחב – חלק 1: מיפוי אובייקטיבי מלא, מילון נתונים (Data Dictionary) וסיווג משתנים**

מסמך זה מהווה את ההרחבה המדוקדקת לנקודה מספר 1. הוא מפרק את המערכת לגורמים האטומיים ביותר שלה, מגדיר את חוזי התקשורת (Interfaces) בין המודולים, ומספק מילון נתונים קפדני המסווג כל משתנה במערכת על פי רמת האמינות שלו. אין כאן מקום לפרשנות מפתח; זהו המפרט המחייב לכתיבת הקוד.

### 1.1 מיפוי מודולים לוגיים (The "Model" Layer - Pure Logic)

שכבת הלוגיקה העסקית מופרדת לחלוטין מה-DOM ומה-BOM (Browser Object Model). כל מודול להלן הוא פונקציה טהורה (Pure Function) או מחלקה סטטית המקבלת קלט מוגדר ומחזירה פלט דטרמיניסטי, ללא תלויות חיצוניות (Zero Dependencies).

#### א. `AstroEngine` & `LiturgicalCalendar` (מנוע אסטרונומי ולוח עברי)
*   **תפקיד:** חישוב זמני שקיעה מדויקים (לפי אלגוריתם NOAA) והמרת תאריכים לועזיים לעבריים לצורך זיהוי שבתות, חגים וזמני ישיבות (חורף/קיץ/אלול).
*   **קלט:** אובייקט `Date` לועזי, קואורדינטות גיאוגרפיות (`lat`, `lon`).
*   **פלט:** אובייקט המכיל: `{ isShabbat: boolean, isHoliday: boolean, zman: string, sunsetDecimal: number }`.
*   **הערה אדריכלית:** המנוע הקיים בקובץ v14 מכיל שגיאה מתמטית קריטית בחישוב ה-Hour Angle וה-Equation of Time (סטייה של שעות בשקיעה). המודול יוחלף בלוגיקה מתוקנת המבוססת על חישובי רדיאנים מדויקים, ללא ייבוא ספריות כגון `SunCalc`.

#### ב. `DataCleanser` (מנוע טיוב נתונים)
*   **תפקיד:** זיהוי וניקוי כפילויות בקבצי CSV של חח"י (תופעת מוני אימות מקבילים).
*   **קלט:** מערך אובייקטים גולמי מפרסור ה-CSV.
*   **פלט:** מערך נקי שבו רשומות בעלות מפתח זהה (`תאריך_שעה_סוגמונה`) אוחדו לממוצע מתמטי, בתוספת אובייקט מטא-דאטה המדווח על כמות הכפילויות וסטיית התקן ביניהן.

#### ג. `DataNormalizer` (מנוע סינתזת נתונים - IPF)
*   **תפקיד:** יצירת סדרה שעתית סינתטית (8,760 רשומות) כאשר הלקוח מספק רק צריכה שנתית כוללת וסוג נכס.
*   **קלט:** `annualKwh` (מספר), `propertyType` (מחרוזת המפנה למטריצת התפלגות).
*   **לוגיקה פנימית:** שימוש באלגוריתם Iterative Proportional Fitting (15 איטרציות) כדי לאלץ את הנתונים לעמוד בו-זמנית ביעדי עונה (חורף/קיץ/מעבר), יעדי תעו"ז (פסגה/שפל) ויעדי ימי שבוע (חול/סופ"ש).
*   **פלט:** מערך אובייקטים `{ dateObj, kwh }` המדמה קובץ חח"י תקין.

#### ד. `EnergySimulator` (מכונת מצבי אגירה - Dispatch State Machine)
*   **תפקיד:** סימולציה כרונולוגית (שעה-אחר-שעה) של התנהגות הסוללה מול צריכת הלקוח בפועל.
*   **קלט:** סדרת נתונים שעתית (8760 שורות), `batteryUsableKwh`, `inverterPowerKw` (מגבלת C-rate), `eff_charge`, `eff_discharge`.
*   **לוגיקה פנימית:** ניהול משתנה מצב `currentSoC` (State of Charge). בשעות שפל: טעינה עד למגבלת הממיר או הקיבולת (המוקדם מביניהם), תוך החלת `eff_charge`. בשעות פסגה: פריקה לכיסוי הצריכה, מוגבלת ב-`currentSoC` ובממיר, תוך החלת `eff_discharge`.
*   **פלט:** אובייקט תוצאות הכולל: חיסכון כספי נטו (ארביטראז'), אחוז כיסוי פסגה, ומספר מחזורי טעינה שנתיים.

#### ה. `TariffCalculator` (מנוע תעריף מדורג)
*   **תפקיד:** חישוב תעריף הזרמה משוקלל (Staircase FIT) על בסיס מדרגות רגולטוריות.
*   **קלט:** `P0` (הספק קיים), `P1` (הספק כולל), `hasBattery` (בוליאני), `isUrban` (בוליאני).
*   **לוגיקה פנימית:** שימוש קפדני ב-`Math.max(0, Math.min(total, tierMax) - prevTierMax)` לכל מדרגה, כדי למנוע חישובים שליליים כאשר P0 חוצה מדרגות. החלת הנחת 5% על מדרגת 15-100 אם `hasBattery` חיובי.
*   **פלט:** תעריף משוקלל (מספר, ₪ לקוט"ש).

#### ו. `FinancialModel` & `TaxEngine` (מנוע תזרים ומיסוי)
*   **תפקיד:** בניית תזרים מזומנים ל-25 שנה וחישוב מדדי כדאיות.
*   **קלט:** CAPEX, OPEX, תפוקה שנתית, תעריף משוקלל, פרמטרי הלוואה (אחוז, ריבית, שנים), סטטוס מס.
*   **לוגיקה פנימית:** 
    *   פירוק הלוואה ל-PPMT (קרן) ו-IPMT (ריבית) ברזולוציה חודשית המוכפלת לנתון שנתי.
    *   **TaxEngine:** חישוב מסלול כפול לאדם פרטי (פטור נשחק מול 10% שטוח) ובחירת המינימום. לעסק: ניכוי פחת מואץ (25% ל-4 שנים) וניכוי IPMT לפני חישוב 23% מס חברות.
*   **פלט:** מערכי תזרים (Project ו-Equity), IRR (מחושב נומרית ע"י Newton-Raphson), NPV, LCOE.

#### ז. `CryptoEngine` (מפענח נתוני טופס)
*   **תפקיד:** פענוח קבצי `.json.enc` המגיעים מ-`Form.html` (v3.0).
*   **קלט:** מחרוזת Base64 של הקובץ המוצפן.
*   **לוגיקה פנימית:** שימוש ב-`crypto.subtle.importKey` ו-`crypto.subtle.decrypt` (AES-GCM) עם המפתח המקודד.
*   **פלט:** אובייקט JSON גלוי המכיל את היררכיית הצרכנים.

### 1.3 ניהול מצב וזרימת נתונים (State Management & Data Flow)

הארכיטקטורה אוסרת על העברת נתונים קריטיים בין חלונות דפדפן באמצעות `localStorage` עקב שבירות מובנית (CORS, Incognito, דריסת נתונים). 

**זרימת הנתונים התקנית (The Data Pipeline):**
1. **אתחול (Initialization):** `Index.html` (ה-CRM) פותח את המחשבון באמצעות URL Parameters: `?page=calculator&clientId=BS-1234&roofArea=150&p0=15`.
2. **עיבוד (Processing):** המחשבון שואב את הפרמטרים מה-URL, מאתחל את ה-State הפנימי (אובייקט JS בזיכרון הריצה בלבד), ומריץ את המודלים הלוגיים.
3. **סיום ושמירה (Commit):** בלחיצה על "שמור תוצאות", המחשבון אורז את כל הפלט (IRR, NPV, CAPEX, לוח סילוקין) לאובייקט JSON מוקשח (Strict Schema) ושולח אותו ישירות לשרת ה-GAS באמצעות `google.script.run.saveCustomerData(payload)`.
4. **הפקה (Rendering):** `PrintQuote.html` נפתח עם `?clientId=BS-1234`, שואב את ה-JSON המלא מהשרת (ולא מ-`localStorage`), ומרנדר את ה-PDF כולל כל המדדים הכלכליים.

### 2.1 כפילויות ארכיטקטוניות ושבר בזרימת הנתונים (Architectural Duplications & Pipeline Fractures)

הכשלים בקטגוריה זו מונעים מהמערכת לתפקד כ-Single Source of Truth ויוצרים מצב שבו עדכון לוגיקה דורש תחזוקה במספר מוקדים במקביל.

#### א. פרדוקס המחשבון הכפול (`calcView` מול `solar-calculator-spa.html`)
*   **הסתירה:** קובץ `Index.html` (ה-CRM) מכיל בתוכו (שורות 203-291) עותק קשיח ומוטמע של מנוע החישוב הפיננסי (`runFinancialModel`, `pmt`, `npv`, `irr`). במקביל, קיים קובץ חיצוני `solar-calculator-spa.html` המכיל את אותה לוגיקה.
*   **הפער:** העותק המוטמע ב-`Index.html` התיישן ואינו כולל את התיקונים שבוצעו בקבצים החיצוניים (למשל, תיקון אנומליית השבת בחורף או תיקון מדרגות התעריף).
*   **השלכה אנטרפרייזית:** איש מכירות המשתמש ב-`Index.html` יקבל תוצאות פיננסיות שונות לחלוטין מאלו שיופקו אם יפתח את המחשבון החיצוני. זוהי הפרה חמורה של עקרון DRY.

#### ב. פרדוקס איסוף הצרכנים המשולש (The Triple-Consumer Data Entry)
*   **הסתירה:** נתוני הרגלי הצריכה של הלקוח נאספים בשלוש דרכים שונות שאינן מתקשרות זו עם זו:
    1.  ב-`Index.html` (סעיף "2. צרכנים"): איסוף בסיסי של שורות טקסט.
    2.  ב-`Form.html` (v3.0): איסוף עשיר ומורכב הכולל היררכיית מיקום/קטגוריה, וטווחי תאריכים עבריים/לועזיים.
    3.  במחשבונים (1, 3, 4): הסתמכות על קובץ CSV מחברת החשמל.
*   **הפער:** איש מכירות המזין נתונים ב-`Index.html` ואז שולח ללקוח את `Form.html` מייצר שתי ישויות מידע סותרות לאותו לקוח במסד הנתונים.

#### ג. שבר חוזה הנתונים בייצוא להדפסה (PrintQuote Data Binding Failure)
*   **הסתירה:** המחשבון שומר את תוצאותיו ל-`localStorage` תחת המפתח `transferredCalcData`. קובץ `Index.html` קורא את הנתונים, אך דוחס את המדדים הפיננסיים הקריטיים (IRR, NPV, חיסכון שנתי, קיבולת אגירה) לתוך שדה טקסט חופשי יחיד בשם `analysisNotes`.
*   **הפער:** קובץ `PrintQuote.html` (מחולל ה-PDF) מתוכנת לחפש שדות מובנים (כגון `annualSavings`, `roiPercentage`), אך אלו מוגדרים כ-`readonly` ב-`Index.html` ולעולם אינם מקבלים ערך מהמחשבון.
*   **השלכה אנטרפרייזית:** הצעת המחיר הסופית המופקת ללקוח אינה מציגה את נתוני הרווחיות, מה שהופך את כל תהליך החישוב לעקר מבחינה עסקית.

### 2.2 סתירות מתמטיות והנדסיות (Mathematical & Engineering Contradictions)

בקטגוריה זו נמצאו פערים בין חוקי הפיזיקה וההנדסה לבין המימוש בקוד, וכן סתירות בין גרסאות המחשבון השונות.

#### א. באג ה-AC/DC בחישוב ה-CAPEX (The AC/DC CAPEX Bug)
*   **הסתירה:** בקבצים 3 ו-4, הקוד מבצע את הפעולה הבאה: `const pAc = targetKwp / 1.3;`. לאחר מכן, הוא משתמש ב-`pAc` המוקטן כדי לחשב את עלות ההקמה: `pvCost = pAc * capexPV`.
*   **הפער:** עלות הקמה (CAPEX) מתומחרת תמיד לפי הספק הפאנלים (DC), ולא לפי הספק הממיר (AC).
*   **השלכה אנטרפרייזית:** המערכת מוזילה את עלות הפרויקט ב-23% באופן פיקטיבי. מערכת של 100 קוו"ט מתומחרת כאילו הותקנו רק 76.9 קוו"ט, מה שמנפח את ה-IRR לממדים אבסורדיים. במקביל, התפוקה (Revenue) מחושבת לפי ה-DC המלא, מה שיוצר חוסר עקביות פנימי באותה פונקציה.

#### ב. מודל עלות האגירה (Flat vs. Split Model)
*   **הסתירה:** 
    *   קבצים 3 ו-4 מניחים עלות אגירה שטוחה: `3,500 ₪ / קוט"ש`.
    *   קבצים 1 ו-2 (התואמים לאקסל המקורי) מניחים מודל מפוצל: `510 ₪ / קוט"ש (תאים) + 52,330 ₪ (ממיר היברידי קבוע)`.
*   **הפער:** המודל השטוח מעוות לחלוטין את כדאיות הגדלת הסוללה. הוספת קוט"ש שולי עולה בפועל רק 510 ₪, אך המודל השטוח מעניש את האופטימיזציה ב-3,500 ₪ לכל קוט"ש נוסף.

#### ג. מודל שחיקת הפאנלים (Degradation Models)
*   **הסתירה:**
    *   קובץ 1 ו-2: שחיקה לינארית של `0.25%` בשנה.
    *   קובץ 3 ו-4: שחיקה מעריכית (Exponential) של `0.35%` בשנה.
*   **הפער:** בשתי הגרסאות חסר לחלוטין יישום של תופעת ה-LID (Light-Induced Degradation) המפחיתה כ-1.5% מהתפוקה כבר בשנה הראשונה.

#### ד. עיוות עלויות התפעול (OPEX Calculation Mismatch)
*   **הסתירה:** כאשר נבחרת אגירה, ה-OPEX קופץ מ-80 ₪ ל-250 ₪.
*   **הפער:** הקוד מכפיל את ה-250 ₪ ב**הספק הפאנלים (קוו"ט)** במקום בנפח הסוללה. לקוח עם 100 קוו"ט פאנלים וסוללה זעירה של 10 קוט"ש ישלם 25,000 ₪ תפעול שנתי, בעוד לקוח עם 10 קוו"ט פאנלים וסוללה ענקית של 100 קוט"ש ישלם רק 2,500 ₪.

### 2.3 פערי רגולציה, מיסוי ומימון (Regulatory & Financial Gaps)

המודל הפיננסי מכיל סתירות חוקיות החושפות את המערכת להטעיית לקוחות.

#### א. הכלאת מסלולי המס הפרטי (The Tax Track Hybrid Bug)
*   **הסתירה:** הקוד מחשב מס לאדם פרטי כך: `if (taxableIncome > 25000) tax = (taxableIncome - 25000) * 0.10;`.
*   **הפער:** חוק עידוד השקעה באנרגיות מתחדשות אינו עובד כך. קיימים שני מסלולים נפרדים:
    1.  מסלול פטור: פטור מלא עד 27,900 ₪ (נכון ל-2026), הנשחק לינארית מעל סכום זה.
    2.  מסלול מס מופחת: 10% מס **מהשקל הראשון** (לא על העודף!) עד תקרה של 120,000 ₪.
*   **השלכה אנטרפרייזית:** המחשבון מציג חבות מס נמוכה משמעותית מהמציאות עבור לקוחות פרטיים עם הכנסות בינוניות-גבוהות.

#### ב. היפוך לוגיקת המע"מ (VAT Application Reversal)
*   **הסתירה:** הקוד מבצע `capex /= 1.17` עבור לקוח עסקי, ומשאיר את ה-CAPEX ללא שינוי עבור לקוח פרטי.
*   **הפער:** המחירים במערכת (למשל 2,400 ₪ לקוו"ט) מוזנים **ללא מע"מ**. לכן, עסק (שמקזז מע"מ) אמור לשלם את מחיר הבסיס, ואילו אדם פרטי אמור לשלם `capex *= 1.18` (מע"מ 2026 הוא 18%, לא 17%). הקוד הפך את היוצרות והשתמש בשיעור מע"מ מיושן.

#### ג. שלילת פרמיה אורבנית ב-Zero Export
*   **הסתירה:** פונקציית `calculateBlendedFitTariff` מחזירה `0` מיד אם `zeroExport === true`, ובכך מדלגת על שורת הוספת הפרמיה האורבנית (`+ 0.06`).
*   **הפער:** רגולטורית, צריכה עצמית מאחורי המונה באזור עירוני זכאית לפרמיה האורבנית כהפחתה מהחשבון. המערכת שוללת מהלקוח הטבה חוקית.

#### ד. סתירת מקור תעריף הארביטראז' (Arbitrage Tariff Source)
*   **הסתירה:**
    *   קבצים 1, 3, 4: מחשבים את רווח האגירה על בסיס תעריפי התעו"ז הרשמיים (למשל 1.4597 ₪ בקיץ).
    *   קובץ 2 (המלצה): משתמש בטבלת "תעריף משלים" נפרדת לחלוטין (`compTariff`), המפוצלת לפי גודל מערכת (עד 300 קוו"ט / מעל 300 קוו"ט), ומשלבת אותם עם התעו"ז הרשמי לפי אחוז "שימוש עצמי חיצוני" (`externalBlendPct`).
*   **הפער:** קובץ 2 הוא היחיד שתואם במדויק את האקסל המקורי של מחלקת ההנדסה. שאר הקבצים מפשטים את המודל ומציגים רווחיות שגויה.

### 2.4 פערי זמנים, אסטרונומיה ואלגוריתמים (Chronological & Algorithmic Discrepancies)

כשלים בטיפול במימד הזמן גורמים לסיווג שגוי של נתוני הצריכה.

#### ג. סימולציה שעתית מול הערכה סטטית (Static vs. Simulated Arbitrage)
*   **הסתירה:**
    *   קובץ 3 ו-4: מניחים 300 ימי ארביטראז' בשנה בתעריף קיץ בלבד (הערכה גסה ושגויה).
    *   קובץ 2: מחשב סטטיסטית לפי 83 ימי קיץ ו-90 ימי חורף.

*   **הפער:** רק קובץ 1 מתחשב בעובדה שבימים מסוימים אין מספיק צריכת פסגה כדי לרוקן את הסוללה, או שאין מספיק זמן שפל כדי לטעון אותה במלואה.

### 3.1 עקרונות יסוד אדריכליים (Core Architectural Principles)

הארכיטקטורה החדשה תוכפף לשלושה חוקי ברזל:
1. **Single Source of Truth (מקור אמת יחיד):** לוגיקה עסקית (כגון חישוב תעריף או מס) תיכתב פעם אחת בלבד, במודול ייעודי. אין לשכפל קוד חישוב בין דפים שונים.
2. **Zero DOM Dependency במודלים (Agnostic Logic):** שכבת המודל (המתמטיקה והאלגוריתמים) לא תכיר את קיומו של הדפדפן. היא לא תקרא ערכים מ-`document.getElementById` ולא תכתוב ל-`innerHTML`. היא תקבל אובייקטי נתונים (JSON) ותחזיר אובייקטי נתונים. הדבר יבטיח יכולת בדיקה (Testability) מוחלטת מחוץ לדפדפן.
3. **Stateless Cross-Window Communication:** ביטול מוחלט של ההסתמכות על `localStorage` להעברת נתונים קריטיים בין חלונות. התקשורת תתבצע דרך מסד הנתונים (Google Sheets) באמצעות ה-Backend (`code.js`), כאשר ה-URL משמש רק להעברת מזהים (`?clientId=X`).

### 3.3 מודל השכבות והפרדת רשויות (Layered Architecture)

המערכת תבנה בשלוש שכבות מבודדות. תקשורת בין השכבות תתבצע אך ורק באמצעות העברת אובייקטי נתונים (Data Transfer Objects - DTOs).

#### שכבה 1: The Model (Pure Logic Layer)
שכבה זו תכיל מחלקות סטטיות. אסור לה להכיל שום קריאה ל-`window`, `document`, או `localStorage`.

1.  **`TariffEngine`**:
    *   *אחריות:* חישוב תעריפי הזרמה וארביטראז'.
    *   *מתודות:* `calculateStaircaseFit(p0, pAc, hasBattery, isUrban)`, `getArbitrageValue(season, kwp)`.
2.  **`PhysicsEngine`**:
    *   *אחריות:* חישובי תפוקה, שחיקה, והמרות אנרגיה.
    *   *מתודות:* `calculateAnnualYield(kwp, azimuth, shading, degradation, year)`, `calculateDynamicSelfConsumption(batteryKwh, dailyYield)`.
3.  **`DispatchSimulator`**:
    *   *אחריות:* ניהול מכונת המצבים של הסוללה.
    *   *מתודות:* `runHourlySimulation(timeSeries, batteryKwh, inverterKw, effCharge, effDischarge)`.
4.  **`FinanceEngine`**:
    *   *אחריות:* בניית תזרים, מיסוי, וחישובי ערך.
    *   *מתודות:* `buildCashflow(capex, opex, revenues, loanParams, taxStatus)`, `calculateIRR(cashflows)`, `calculateNPV(rate, cashflows)`.
5.  **`CryptoAstroEngine`**:
    *   *אחריות:* פענוח נתוני טופס וחישובי לוח שנה.
    *   *מתודות:* `decryptFormData(base64String, key)`, `getHebrewDate(date)`, `getAccurateSunset(date, lat, lon)`.

#### שכבה 2: The Controller (Orchestration Layer)
שכבה זו (שתשב בתוך `solar-calculator-spa.html`) תנהל את זרימת העבודה:
1.  קריאת פרמטרים מה-URL (למשל `clientId`).
2.  קריאה ל-Backend (`google.script.run`) לשליפת נתוני לקוח קיימים.

6.  העברת התוצאות לפונקציות הרינדור של ה-View.
7.  שליחת התוצאות הסופיות חזרה ל-Backend לשמירה.

**תרחיש זרימת עבודה מלא (End-to-End Workflow):**

### חלופה א': Monolithic SPA with Async Yielding & Template Includes (החלופה הפרגמטית)

בחלופה זו, המערכת תרוץ כולה על ה-Main Thread של הדפדפן, אך תשתמש בטכניקות אסינכרוניות כדי למנוע חסימת ממשק (UI Blocking) בעת חישובים כבדים. הקוד יפוצל לוגית לקבצי `.html` נפרדים ב-GAS, שיוזרקו לקובץ הראשי בעת הרינדור בשרת.

**1. מבנה הקבצים ב-GAS:**
*   `Calculator.html` (השלד הראשי וה-DOM)
*   `Style.html` (כלל ה-CSS)
*   `CoreEngine.html` (מכיל תגית `<script>` עם כל המחלקות הסטטיות: `TariffEngine`, `DispatchSimulator` וכו')
*   `AppController.html` (מכיל תגית `<script>` המנהלת את ה-State וה-DOM)
*   *ב-`code.js` יבוצע:* `template.evaluate()` עם פונקציית `include()` להזרקת הקבצים.

**2. ניתוח ביצועים (Performance):**
*   **סיבוכיות זמן (Time Complexity):** $O(N)$ עבור סימולציית הדיספאץ' ונירמול ה-IPF, כאשר $N=8760$ (שעות בשנה). בסביבת V8 מודרנית, לולאה כזו רצה ב-10-20 מילישניות. עם זאת, כאשר מריצים אופטימיזציה (Grid Search) הבודקת 20 גדלי סוללה שונים, הסיבוכיות הופכת ל-$O(M \cdot N)$ (כאשר $M$ הוא מספר הגדלים). זה עלול לקחת 200-400 מילישניות ולגרום ל"גמגום" (Jank) ב-UI.
*   **פתרון Async Yielding:** לולאת האופטימיזציה תפוצל באמצעות `setTimeout(..., 0)` או `requestAnimationFrame` בין כל בדיקת גודל סוללה. הדבר יאפשר לדפדפן לרנדר אנימציית טעינה (Spinner) ולשמור על 60FPS.
*   **סיבוכיות מקום (Space Complexity):** $O(N)$. החזקת מערך של 8,760 אובייקטים בזיכרון דורשת כ-2-3MB של RAM. זהו נתון זניח לחלוטין עבור דפדפנים מודרניים.

**3. תחזוקתיות (Maintainability):**
*   **גבוהה מאוד.** למרות שהקוד מוגש כקובץ יחיד ללקוח, סביבת הפיתוח ב-GAS נשארת מודולרית. מפתחים יכולים לערוך את `CoreEngine.html` מבלי לגעת ב-UI.
*   היעדר תלויות חיצוניות (Zero Dependencies) למעט ספריות ה-CDN המאושרות (PapaParse, ExcelJS, Chart.js) מבטיח שהקוד לא יישבר עקב עדכוני ספריות (NPM Rot).

**4. ניהול שגיאות (Error Handling):**
*   כל מודול ב-`CoreEngine` יעטוף את הלוגיקה שלו ב-`try/catch` ויזרוק שגיאות מותאמות אישית (Custom Errors), למשל: `throw new Error("DISPATCH_SIMULATION_FAILED: Invalid SoC")`.
*   ה-`AppController` יתפוס שגיאות אלו ויציג Toast Notification ידידותי למשתמש, תוך ביצוע Graceful Degradation (למשל, אם סימולציית האגירה קורסת, המערכת תציג את תוצאות הסולארי-בלבד ותשבית את כרטיסיית האגירה, במקום להקריס את כל הדף).

### חלופה ב': Web Worker Architecture via Blob URLs (חלופת הביצועים המקסימליים)

בחלופה זו, כל הלוגיקה המתמטית הכבדה (סינתזת IPF, סימולציית דיספאץ', בניית תזרים 25 שנה) תופרד לחלוטין מה-Main Thread ותרוץ ברקע באמצעות Web Worker.

**1. אתגר היישום בסביבת GAS:**
מכיוון ש-GAS אינו מאפשר הגשת קבצי `.js` טהורים עם כותרות מתאימות ל-Web Workers, יש להשתמש בטכניקת Blob URL. קוד ה-`CoreEngine` ייכתב כמחרוזת (או יישאב מתגית `<script type="text/worker">`), יומר ל-Blob, ויוזן ל-Worker.

```javascript
// דוגמה ארכיטקטונית ליישום ב-GAS:
const workerCode = document.getElementById('worker-core-engine').textContent;
const blob = new Blob([workerCode], { type: 'application/javascript' });
const worker = new Worker(URL.createObjectURL(blob));

worker.postMessage({ action: 'RUN_DISPATCH', payload: { series: data, batKwh: 50 } });
```

**2. ניתוח ביצועים (Performance):**
*   **סיבוכיות זמן:** זהה לחלופה א' ($O(M \cdot N)$), אך זמן הריצה *המורגש* (Perceived Performance) הוא אפס. ה-Main Thread פנוי לחלוטין, האנימציות חלקות, ואין צורך ב-Async Yielding מורכב.
*   **סיבוכיות מקום ותקורת תקשורת (Overhead):** העברת מערך של 8,760 אובייקטים ל-Worker דורשת Serialization (העתקה עמוקה באמצעות Structured Clone Algorithm). תהליך זה צורך זיכרון כפול (לזמן קצר) ומוסיף תקורת זמן של כ-5-10 מילישניות להעברת ההודעה.

**3. תחזוקתיות (Maintainability):**
*   **נמוכה-בינונית.** דיבוג (Debugging) של Web Workers המבוססים על Blob URLs הוא קשה משמעותית. ה-Stack Traces לרוב אינם מצביעים על השורה הנכונה בקוד המקור.
*   הקוד הופך למבוזר: יש לנהל פרוטוקול תקשורת (Message Passing Protocol) בין ה-Controller ל-Worker, מה שמוסיף Boilerplate רב (ניהול Promises סביב `worker.onmessage`).

**4. ניהול שגיאות (Error Handling):**
*   שגיאות בתוך ה-Worker אינן מקריסות את ה-UI.
*   ה-Worker יתפוס שגיאות וישלח חזרה אובייקט שגיאה מובנה: `postMessage({ status: 'ERROR', code: 'MATH_FAULT', details: e.message })`.
*   ה-Controller יאזין ל-`worker.onerror` כדי לתפוס קריסות קריטיות (OOM - Out of Memory) ויבצע אתחול מחדש (Reboot) ל-Worker במקרה הצורך.

### 5.1 תשתית הבדיקות העצמאית (The Vanilla Assertion Framework)

מכיוון שחישובי אנרגיה ופיננסים מועדים לשגיאות עיגול ונקודה צפה (Floating Point Inaccuracies), נבנתה מחלקת `Assert` ייעודית המטפלת בהשוואות מתמטיות באמצעות אפסילון (Epsilon), וכן בהשוואת מבני נתונים מורכבים (Deep Equal).

קוד זה יוזרק לתחתית קובץ ה-`CoreEngine.js` ויהיה זמין להרצה מקונסולת המפתחים (Developer Tools).

```javascript
const Assert = {
    EPSILON: 1e-5,
    
    // השוואת ערכים מתמטיים עם סובלנות לשגיאות נקודה צפה
    almostEqual: function(actual, expected, testName) {
        if (Math.abs(actual - expected) > this.EPSILON) {
            console.error(`❌ [FAIL] ${testName}\n   Expected: ${expected}\n   Actual:   ${actual}`);
            throw new Error(`Test Failed: ${testName}`);
        }
        console.log(`✅ [PASS] ${testName}`);
    },

    // השוואת ערכים בוליאניים או מחרוזות
    strictEqual: function(actual, expected, testName) {
        if (actual !== expected) {
            console.error(`❌ [FAIL] ${testName}\n   Expected: ${expected}\n   Actual:   ${actual}`);
            throw new Error(`Test Failed: ${testName}`);
        }
        console.log(`✅ [PASS] ${testName}`);
    },

    // השוואת מערכים (למשל, תזרימי מזומנים)
    arrayAlmostEqual: function(actualArr, expectedArr, testName) {
        if (actualArr.length !== expectedArr.length) {
            console.error(`❌ [FAIL] ${testName} | Length mismatch`);
            throw new Error(`Test Failed: ${testName}`);
        }
        for (let i = 0; i < actualArr.length; i++) {
            if (Math.abs(actualArr[i] - expectedArr[i]) > this.EPSILON) {
                console.error(`❌ [FAIL] ${testName} | Mismatch at index ${i}\n   Expected: ${expectedArr[i]}\n   Actual:   ${actualArr[i]}`);
                throw new Error(`Test Failed: ${testName}`);
            }
        }
        console.log(`✅ [PASS] ${testName}`);
    }
};
```

### 5.2 מערך בדיקות הרגולציה והתעריפים (Regulatory & Tariff Suite)

חטיבת בדיקות זו מוודאת שהבאגים הקריטיים שאותרו בקוד ההיסטורי (כגון באג ה-P0 השלילי והשמטת הפרמיה האורבנית) תוקנו לחלוטין ואינם חוזרים (Regression Testing).

```javascript
function testTariffEngine() {
    console.group("--- Running TariffEngine Tests ---");
```

### 5.4 מערך בדיקות הפיזיקה וסימולטור האגירה (Physics & Dispatch Suite)

זהו המבחן הקריטי ביותר. הוא מוודא שמכונת המצבים של הסוללה אינה מפרה את חוק שימור האנרגיה (Conservation of Energy) ושמגבלות החומרה (C-rate) נאכפות.

```javascript
function testDispatchSimulator() {
    console.group("--- Running DispatchSimulator Tests ---");

    // יצירת סדרת נתונים פיקטיבית קצרה (Mock Series)
    const mockSeries = [
        { isPeak: false, actualKwh: 5 },  // שעת שפל: צריכה 5. ניתן לטעון.
        { isPeak: true,  actualKwh: 10 }, // שעת פסגה: צריכה 10. דורש פריקה.
        { isPeak: true,  actualKwh: 20 }  // שעת פסגה: צריכה 20. דורש פריקה.
    ];

    const batKwh = 50; // קיבולת שמישה
    const invKw = 25;  // מגבלת ממיר (0.5C)
    const effCharge = 0.93;
    const effDischarge = 0.94;

    const results = DispatchEngine.runHourlySimulation(mockSeries, batKwh, invKw, effCharge, effDischarge);

    // 1. חוק שימור האנרגיה (Conservation of Energy)
    // האנרגיה שנכנסה לסוללה (בניכוי הפסדי טעינה) פחות האנרגיה שיצאה ממנה (בתוספת הפסדי פריקה) 
    // חייבת להיות שווה לשינוי במצב הטעינה (Delta SoC).
    const energyIn = results.totalCharged * effCharge;
    const energyOut = results.totalDischarged / effDischarge;
    const deltaSoC = results.finalSoC - results.initialSoC;
    
    Assert.almostEqual(energyIn - energyOut, deltaSoC, "Physics: Conservation of Energy Maintained");

    // 2. אכיפת מגבלת ממיר (Inverter Bottleneck)
    // וידוא שבשום שעה לא נפרק או נטען יותר ממה שהממיר מאפשר (25kW * 1 hour = 25kWh)
    const maxDischargeInOneHour = Math.max(...results.hourlyLogs.map(log => log.discharged));
    const maxChargeInOneHour = Math.max(...results.hourlyLogs.map(log => log.charged));
    
    if (maxDischargeInOneHour > invKw || maxChargeInOneHour > invKw) {
        throw new Error("Physics: Inverter C-rate limit breached!");
    }
    console.log("✅ [PASS] Physics: Inverter limits enforced");

    console.groupEnd();
}
```

### 5.6 אסטרטגיית הרצה ואינטגרציה (Execution Strategy)

מכיוון שהמערכת רצה ב-Google Apps Script ומוגשת כ-HTML, לא ניתן לחבר אותה ל-CI/CD Pipeline מסורתי (כגון GitHub Actions). לכן, אסטרטגיית ההרצה תהיה כדלקמן:

1.  **Master Test Runner:** תוגדר פונקציה גלובלית `runAllSystemTests()` שתאגד את כל חטיבות הבדיקה לעיל.
2.  **Hidden Trigger:** בממשק המשתמש (UI) של המחשבון, לחיצה משולשת (Triple Click) על מספר הגרסה בתחתית הדף תפעיל את ה-Test Runner.
3.  **Console Output:** התוצאות יודפסו לקונסולת הדפדפן (F12) בפורמט קריא וברור.
4.  **Pre-Flight Check:** לפני כל שמירת נתונים לשרת (`saveCustomerData`), המערכת תריץ ברקע בדיקת שפיות (Sanity Check) מהירה (למשל, וידוא ש-IRR אינו עולה על 100% וש-NPV אינו שלילי באופן קיצוני ללא סיבה). אם הבדיקה נכשלת, המערכת תחסום את השמירה ותתריע על "שגיאת חישוב פנימית", כדי למנוע זיהום של מסד הנתונים ב-Google Sheets בנתונים שגויים.
