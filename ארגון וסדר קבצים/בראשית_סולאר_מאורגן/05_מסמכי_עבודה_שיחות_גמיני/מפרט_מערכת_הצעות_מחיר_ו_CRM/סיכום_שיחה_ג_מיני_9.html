מסמך העברת פרויקט (Handoff) – מערכת CRM, איסוף נתונים וחישוב סולארי

1. תיאור כללי של הפרויקט

המערכת, המפותחת עבור "בראשית סולאר", היא חבילת כלים מבוססת Web (HTML/JS/CSS) הרצה על גבי תשתית Google Apps Script (GAS) עם מסד נתונים ב-Google Sheets.

מטרת המערכת: ניהול לקוחות, הפקת הצעות מחיר למערכות סולאריות, איסוף קפדני של נתוני צריכת חשמל (מכשירי חשמל) מהלקוח עצמו, והרצת סימולציות כדאיות פיננסיות והנדסיות (כולל מערכות אגירה/סוללות) על בסיס פרופיל הצריכה.

משתמשים:

  • נציגי מכירות / מהנדסים: משתמשים במערכת ה-CRM (Index.html) ובמחשבון ההמלצה (מחשבון_המלצת_מערכת.html).
  • לקוחות הקצה: מקבלים לינק ייעודי למילוי טופס איסוף נתוני מכשירים (Form.html).

2. רשימת כל היכולות והפיצ'רים שמומשו

  • מערכת CRM (Index): חיפוש לקוחות קיים ב-Sheets, בניית הצעת מחיר דינמית (פאנלים, ממירים, סוללות), בחירת תמונות מתוך ה-Sheets או העלאת תמונות מקומיות, ושמירת נתונים חזרה ל-Sheets.
  • יצירת לינק מותאם ללקוח: כפתור ב-Index שמייצר URL ייעודי המכיל פרמטר clientId. הלינק מועתק אוטומטית ללוח (Clipboard) ונשלח ללקוח למילוי הטופס.
  • טופס איסוף נתונים חכם (Form): טופס למילוי מצאי מכשירי חשמל לפי קטגוריות ומיקומים. הטופס קורא את ה-clientId מה-URL ושואב אוטומטית את פרטי הלקוח (שם, טלפון, וכו') מ-Sheets.
  • הגבלות זמן היררכיות בטופס: הגדרת זמני פעילות ברמת הצרכן הבודד, ברמת הקטגוריה, וברמת המיקום (חדר/מבנה). סוגי ההגבלות:
    • ימים בשבוע: א'-ש'.
    • שעות ביום: 00:00 עד 23:00.
    • תקופות בשנה: כל השנה, שנת לימודים (ספט'-יוני), שנת ישיבות (חורף, קיץ, אלול), או טווחים מותאמים אישית לפי תאריך לועזי או תאריך עברי. ניתן להזין מספר טווחים מרובים במקביל.
  • הצפנת נתונים (Web Crypto API): ייצוא נתוני הטופס מתבצע לקובץ .enc. הקובץ מוצפן לחלוטין (AES-GCM) ואינו קריא למשתמש.
  • מחשבון המלצה: קולט קבצי CSV מחברת החשמל או קבצי .enc מהטופס. מפענח את הקובץ המוצפן ובונה פרופיל צריכה (שפל/פסגה לפי עונות). מבצע סימולציית "דיספאץ' סוללה" לפי תעריפי רשות החשמל, ומחשב IRR, NPV, החזר השקעה ועוד.
  • הגנות נגד העתקה (Anti-Copy) בטופס: חסימת בחירת טקסט (user-select: none), חסימת קליק ימני, חסימת קיצורי מקלדת (Ctrl+C, Ctrl+S) וחסימת הדפסה (Ctrl+P מציג דף שגיאה).

3. אלמנטים ב-HTML ובממשק שנוספו או השתנו

  • כפתורי Toggle (Form.html): הוסרו תיבות הסימון (Checkboxes) וכפתורי הרדיו לבחירת ימים ושעות. הוחלפו בכפתורי Toggle מעוצבים (כפתור שנצבע בירוק בלחיצה ומקבל קלאס selected).
  • רשת ימים מרוכזת: בוטלה הכפילות בבחירת ימים. כעת יש רשת אחת של 7 כפתורים (א'-ש') עם כפתורי פעולה מהירה: "בחר הכל", "נקה הכל", "ימי חול בלבד".
  • ממשק טווחים דינמיים (Form.html): בבחירת תקופה לועזית או עברית מופיע ממשק המאפשר הוספה של שורות טווח (Range) עם כפתור מחיקה לכל שורה. (שימוש ב-addGregorianRange ו-addHebrewRange).
  • תפריטי היררכיה בטופס: בשורת הכותרת של כל "מיקום" ובשורת הכותרת של כל "קטגוריה", נוספו כפתורים מיניאטוריים (btn-header-mini) להגדרת ימים, שעות ותקופות שחלות על כל הצרכנים תחתיהם.
  • כפתור יצירת לינק (Index.html): הוסף כפתור סגול "העתק לינק לטופס נתונים ללקוח זה".

4. חישובים ונוסחאות שמומשו

  • לוגיקת שילוב זמנים היררכית (Intersection): בזמן פענוח קובץ ה-JSON/ENC במחשבון, המערכת מחשבת חיתוך קבוצות (intersectSets) בין ההגדרות של המיקום, הקטגוריה והצרכן. צרכן פועל רק ביום/שעה שמוגדרים גם בצרכן, גם בקטגוריית האב שלו, וגם במיקום שלו. אם אחד מהם מוגדר כ"כל הימים/השעות", הוא אינו מגביל את השאר.
  • חישוב משקל תקופות (Period Ratios): מכיוון שקשה לחשב במדויק משקל של תאריך עברי מול לועזי ביום ספציפי, מומשה פונקציה getCombinedPeriodRatios העושה סימולציה על פני שנת לוח שלמה. היא בודקת עבור כל יום בשנה (365 ימים) האם הוא עובר את חיתוך התקופות של המיקום + קטגוריה + צרכן. התוצאה היא אחוז (Ratio מ-0 עד 1) לכל עונה (חורף, קיץ, מעבר), שבו מכפילים את צריכת הפסגה של המכשיר.
  • אלגוריתם תאריכים עבריים: הוטמע סט פונקציות להמרת תאריך לועזי לעברי (hc_g2j, hc_j2h, חישובי עיבור hc_isLeap ונירמול אדר א'/ב'). המערכת מזהה חגים יהודיים ושבתות לטובת חישוב זמני שפל/פסגה בתעו"ז.
  • הצפנה (AES-GCM): פונקציות encryptJSON ו-decryptJSON. ה-IV נוצר רנדומלית ומצורף לתחילת הקובץ. הקוד הופך למערך בינארי, מקודד ל-Base64 ומוורד למחשב.

5. תיקונים ושינויי כיוון במהלך הדרך (החלטות סופיות)

  • סופי: משיכת נתוני לקוח לטופס דרך השרת (Server-Side Template Injection). במקור ניסינו למשוך את ה-clientId מה-URL בעזרת google.script.url.getLocation. התברר שתוספי דפדפן (Ad-blockers, תרגום וכו') גורמים לקריסה של הסקריפטים בסוף הטעינה (window.onload). התיקון: ב-code.js אנו מזריקים את ה-ID ישירות ל-HTML בזמן יצירת התבנית: <?= clientIdParam ?>, ומריצים את הבקשה ב-DOMContentLoaded לקבלת יציבות מקסימלית.
  • סופי: מזהי (IDs) של חלונות קופצים. במקור עבדנו עם customHoursContainer, אך במהלך מעבר לעיצוב ה-Toggle Buttons שונה השם ל-hoursContainer. זה תוקן סופית ב-Form.html.
  • סופי: איסור מוחלט על שינוי שמות פונקציות קיימות. הייתה דרישה מפורשת לא לשנות פונקציות קיימות, אלא רק להוסיף את פונקציות ה-Hierarchy וה-Ranges מעליהן או בתוכן.

6. מבנה הנתונים

אובייקט הייצוא המוצפן (JSON בתוך קובץ ה-ENC):


{
  "formVersion": "3.0",
  "exportedAt": "ISO String",
  "clientDetails": { "name", "phone", "address", "contract", "filledBy", "notes" },
  "locations": [
    {
      "name": "שם המיקום",
      "consumers": [
        {
          "category": "תאורה",
          "type": "נורות",
          "fields": { "power": 100, "qty": 5 },
          "days": [0,1,2,3,4,5,6], // מערך אינטג'רים נבחרים (צרכן)
          "hours": [17,18,19], // מערך שעות נבחרות (צרכן)
          "periods": { "type": "gregorian", "ranges": [{"start":"09-01", "end":"06-30"}] },
          "catDays": [...], "catHours": [...], "catPeriods": {...}, // הגבלות קטגוריה
          "locDays": [...], "locHours": [...], "locPeriods": {...}  // הגבלות מיקום
        }
      ]
    }
  ]
}

7. סטטוס נוכחי ודברים פתוחים

  • מה עובד: ה-CRM תקין, הזרקת ה-URL תקינה, הטופס עובד עם חסימת העתקה, המחשבון יודע לקרוא את קובץ ה-ENC ולחשב את ההיררכיות המורכבות.
  • נושא אבטחת IP (Intellectual Property): המשתמש שאל כיצד להציג את התוכנה לקונה מבלי שיעתיקו את נוסחאות הפיננסים (ה-Calculator). הסטטוס: כרגע הלוגיקה נמצאת בקובץ ה-HTML בצד הלקוח (Frontend). הוצע למשתמש בעתיד להעביר את פונקציות החישוב (כגון buildCashflow) לצד השרת (code.js) כפתרון קבע. זה עדיין לא מומש בקוד - הקוד הקיים מכיל את הלוגיקה ב-HTML.

8. החלטות והגבלות טכניות

  • הפרויקט נכתב ב-Vanilla JavaScript, HTML, CSS. ללא ספריות Frontend כדוגמת React או Vue.
  • רצון לשמור הכל בקבצים יחידים וארוכים לטובת הזרקה ב-Google Apps Script (HtmlService).
  • ההצפנה מתבצעת באופן מקומי בדפדפן (Web Crypto API) בגלל אופי העבודה.

9. דברים שנפסלו במפורש

  • נפסלה האפשרות למשוך את ה-clientId מקריאת פרמטרים ב-JS של הלקוח בגלל התנגשויות עם תוספי דפדפן, והוחלפה בתבנית שרת.
  • נפסלה כפילות ממשק בהגדרת ימים (היו בעבר צ'קבוקסים וכפתורי רדיו מיותרים - נשארנו עם גריד Toggle אחד לכל מודל).
  • נשללה מסירת עותק נסיוני של התוכנה עם קוד פתוח לקונה פוטנציאלי ללא ערבול (Obfuscation) או העברת קוד לשרת.
נקודות לבירור למודל הבא:
הקוד המועבר אליך כולל את החישובים (buildCashflow, IRR וכו') בתוך ה-Frontend. המשתמש מעוניין להגן על קוד זה בעתיד. ייתכן שהמשימה הבאה שלך תהיה "לעקור" את הפונקציות הללו מ-מחשבון_המלצת_מערכת.html ולהעביר אותן אל code.js עם פונקציית google.script.run. עליך לוודא זאת מול המשתמש.
