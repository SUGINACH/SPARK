מסמך מאוחד — אקולוגיית בראשית סולאר

אפיון הנדסי, אימות הנחות וניתוח פיננסי מקיף לפרויקט מחשבון הסולארי המאוחד. מסמך זה מאחד תשעה מסמכי מקור נפרדים לכדי מקור אמת יחיד (Single Source of Truth), תוך מחיקת כפילויות ואיחוד חלקים חופפים — ללא אובדן ולו פרט אחד מהמידע המקורי.

מסמכי המקור שאוחדו למסמך זה (9): אימות הנחות וניתוח עומק (2026) · אימות הנחות מיקרוסקופי (שלב ג') · אימות הנחות עומק (שלב ב') · אנציקלופדיית אפיון ותכנון הנדסי-פיננסי · ניתוח פיננסי מתקדם (מחשבה פיננסית) · מסמך חפיפה הנדסי · מפרט הנדסי עמוק ומסמך חפיפה · סריקה אטומית (מפרט אימות שלב ג') · סריקה גרעינית (מפרט אימות הנדסי וארכיטקטוני).

כאשר שני מסמכי מקור אימתו אותה נקודה באופן זהה, האימות מופיע כאן פעם אחת. כאשר מסמכי מקור שונים תיעדו את אותה תופעה עם נתונים שונים (למשל אומדן מוקדם מול נתון מדויק מאוחר), שני הנתונים נשמרו יחדיו ומסומנים בתיבת "הערת פער נתונים". כל ההפניות המקוריות ל"קובץ 1 / קובץ 2 / קובץ 3 / קובץ 4" מתייחסות לארבע גרסאות המחשבון ההיסטוריות שנותחו במסמכי המקור (ולא למסמכי המקור עצמם), ונשמרו כלשונן.

חלק 1ארכיטקטורת המערכת ואבולוציית הקבצים

מסמך זה מהווה מקור אמת יחיד (Single Source of Truth) למפתחים. הוא מפרט את כלל הלוגיקות, ההחלטות הארכיטקטוניות, השגיאות שתוקנו, והתנהגויות הממשק שנדרש ליישם במחשבון המאוחד (קובץ 5).

Index.html (מערכת ניהול לאיש מכירות) והכפילויות

נפסל לשימוש עותק מחשבון מוטמע (calcView)

קובץ ה-Index מכיל בתוכו (שורות 203-291) עותק מלא ומוטמע של מנוע החישוב הפיננסי (runFinancialModel, pmt, npv, irr). קוד זה אינו מסונכרן עם קבצי המחשבון החיצוניים (Calculator.html). כל שינוי רגולטורי דרש עדכון כפול.

החלטה ארכיטקטונית: יש למחוק את ה-calcView מ-Index.html לחלוטין. המערכת חייבת להסתמך על מחשבון חיצוני אחד בלבד. Index.html ישמש כ-CRM בלבד.

כפילות נוספת: איסוף "צרכנים" ב-Index.html מתבצע בצורה בסיסית, בעוד ש-Form.html אוסף את אותו מידע בצורה עשירה. יש לאחד את זרימת העבודה כך שאיש המכירות יופנה לטופס המפורט.

Form.html (טופס איסוף נתונים ללקוח — v3.0) וההצפנה

הטופס הנשלח ללקוח מתקדם מאוד: תומך בהיררכיית צרכנים (מיקום → קטגוריה → שורה), טווחי תאריכים בלוח עברי/לועזי, ומושך נתוני לקוח קיימים מהשרת באמצעות ?clientId=X.

פער אינטגרציה קריטי הצפנת AES-GCM

הטופס מייצא קובץ JSON מוצפן (סיומת .json.enc). מפתח ההצפנה מקודד קשיח בטופס:

const FORM_ENCRYPTION_KEY = "BereshitSolarSecureKey1234567890";

הבעיה: אף אחד מגרסאות המחשבונים הנוכחיות אינו מסוגל לפענח קובץ זה. פונקציית ingestJsonApplianceData במחשבון מצפה ל-JSON גלוי במבנה ישן (v1.0), הכולל מערך שעות עבודה שבועי בלבד — בעוד קובץ ה-v3.0 כולל היררכיית מיקום-קטגוריה וטווחי תאריכים עבריים מורכבים (חופש גדול, זמנים ישיבתיים).

הנחיה למפתחים: יש לכתוב מודול פענוח crypto.subtle.decrypt במחשבון המאוחד, ולהתאים את מנוע הסינתזה למבנה הנתונים של v3.0.

PrintQuote.html (מחולל הצעת מחיר PDF)

מנוע רינדור להפקת הצעת מחיר רשמית. שואב נתונים מ-localStorage('pendingQuote').

חור בזרימת הנתונים התעלמות מתוצאות המחשבון

הקובץ אינו קורא בפועל את שדות הסיכום הכלכלי (IRR, NPV, חיסכון שנתי, קיבולת אגירה) מה-State, אלא מסתמך על טקסט חופשי (analysisNotes) או משאיר שדות ריקים.

הנחיה: יש לחווט מחדש את ה-Data Binding כך שיקרא במלואו את האובייקט rawCalculatorData הנשמר ב-DB.

גשר התקשורת השבור (The Broken Bridge)

השיטה הישנה (שנפסלה): המחשבון שומר תוצאות ל-localStorage.setItem('transferredCalcData'), נסגר, ו-Index.html קורא משם.

למה זה נפסל

בסביבת GAS, דפים מוגשים מ-iframes/subdomains שונים (googleusercontent.com). ה-Same-Origin Policy של הדפדפן חוסם לעיתים קרובות שיתוף localStorage בין החלונות, מה שגורם לאובדן נתונים אקראי.

הפתרון הארכיטקטוני:

  • פתיחת המחשבון עם URL Parameters בפתיחה (למשל ?clientId=123&roofArea=100).
  • בסיום החישוב, המחשבון ישלח את הנתונים ישירות לשרת באמצעות google.script.run.saveCustomerData(payload), ולא יסתמך על הדפדפן להעברת המידע.

חלק 2אנציקלופדיית אפיון הנדסי-עסקי

מסמך יסוד זה מגדיר את כלל התרחישים, מקרי הקצה והמשתנים ההנדסיים והפיננסיים של פרויקט בראשית סולאר, ברמת הפירוט הגבוהה ביותר האפשרית — ללא קיצורים — במטרה לשמש כחומר הדרכה ואינטגרציה מוחלט למפתחים, מהנדסים וכלכלני אנרגיה.

2.1 מציאות פיזית ומרחבית — גגות, קונסטרוקציה והצללה

השטח הפיזי של גג הנכס הוא צוואר הבקבוק ההנדסי הראשוני של כל מערכת. משתנים אלו קובעים את גבולות הגזרה המעשיים של התכנון. עלויות הקמה (CAPEX) אינן לינאריות ומשתנות דרסטית לפי סוג הגג הקיים:

  • גג בטון שטוח (Concrete Flat Roof): דורש קונסטרוקציית משולשים מאלומיניום או פלדה מגולוונת ובלוקים של בטון כמשקולות (Ballast) למניעת תזוזה ברוחות חזקות. שטח הגג מנוצל ביעילות נמוכה יותר (כ-7.5 מ"ר לקוו"ט) בגלל הצורך במרווחים בין השורות למניעת הצללה עצמית (Inter-row shading). עלות קונסטרוקציה: כ-600 ₪ לקוו"ט.
  • גג פאנל מבודד / איסכורית (Trapezoidal Metal Roof): סוג הגג הזול והקל ביותר להתקנה. עיגון ישיר לפחי הגג באמצעות "נעליים" מיוחדות ללא משקולות. ניצול שטח מקסימלי (כ-5.5 מ"ר לקוו"ט בלבד). עלות קונסטרוקציה: כ-150 ₪ לקוו"ט.
  • גג רעפים (Tiled Roof): דורש פירוק זמני של רעפים, עיגון ווי פלדה לקורות העץ או הבטון של המבנה, והתקנת מסילות. עבודה איטית ומסוכנת יותר. עלות קונסטרוקציה: כ-450 ₪ לקוו"ט.

הצללה מורכבת (Complex Shading Profiles): מכשולים קבועים על הגג (דודי שמש, מעליות, מזגנים, ארובות, עצים שכנים) מייצרים הצללה דינמית לאורך שעות היום. פאנלים סולאריים מחוברים בטור (String) — פאנל בודד שמוצל ב-50% מוריד את הזרם של ה-String כולו ל-50%.

הפתרון בשטח

התקנת אופטימייזרים (כגון TIGO או SolarEdge) המבצעים אופטימיזציה ברמת הפאנל הבודד (MPPT). זהו רכיב תוספת עלות קשיח ב-CAPEX (כ-200 ₪ לפאנל מוצל) המשפיע על ה-ROI.

2.2 תשתית חשמל ורגולציית רישוי

טופס 4 (תעודת גמר / אישור אכלוס) — תנאי סף חוקי

על פי חוק התכנון והבנייה ותקנות חברת החשמל, חל איסור מוחלט לחבר מערכת סולארית לרשת החשמל במבנה שאין לו טופס 4 מאושר בתוקף. מבנים חקלאיים ישנים, ישיבות באזורים מסוימים או הרחבות בנייה לא חוקיות נתקלים בחסם זה.

⚠️ ההשלכה ההנדסית של היעדר טופס 4

במבנה ללא טופס 4, המערכת יכולה לעבוד אך ורק במצב Off-Grid או Zero-Export מוחלט. מכיוון שחברת החשמל לא תתקין מונה דו-כיווני, המערכת תסבול מקטימה (Curtailment) עצומה של עודפים בצהריים, ודרישת האגירה (סוללה) תזנק פי 3 עד 4 כדי לשמר את האנרגיה לשימוש עצמי בלילה ובערב.

גודל החיבור לרשת (Grid Connection Limits)

הספק המערכת המוזרם לרשת מוגבל פיזית על ידי גודל החיבור הקיים של המבנה לחח"י (מחושב באמפר תלת-פאזי):

הספק חיבור מקסימלי (kW AC) = מתח (400V) × זרם (A) × √3 (1.732) / 1000

דוגמה לקצה חיבור נפוץ: חיבור של 3x80A מאפשר הזרמה מקסימלית של כ-55kW AC בלבד. אם הלקוח מתקין מערכת פאנלים של 100kWp (DC) עם ממיר של 80kW (AC) — המערכת תפרוץ את גבול המתיחה של המנות ותשרוף נתיכים, או שחברת החשמל תפסול את החיבור בביקורת. שדרוג החיבור (למשל מ-3x80A ל-3x250A) כרוך בעלויות חח"י עצומות (עשרות אלפי שקלים) וזמני המתנה ארוכים.

2.3 פרמיה אורבנית וחיוב עלות מערכתית

שני מרכיבי תעריף רגולטוריים קריטיים שנבדקו לעומק בכל סבבי האימות ההנדסיים.

הבאג החוקי: אובדן הפרמיה האורבנית ב-Zero Export

הפרמיה האורבנית מעניקה תוספת של 6 אג' לקוט"ש מיוצר (ליישובים מעל 50,000 תושבים). בקוד המקורי, הפונקציה מאפסת את הפרמיה האורבנית במצב Zero Export משום שאין מכירה פיזית לרשת.

המציאות בשטח: זוהי טעות משפטית. על פי החלטת רשות החשמל, לקוח באזור עירוני המייצר וצורך את האנרגיה בעצמו באתר (צריכה עצמית מאחורי המונה — BTM) זכאי לקבל את זיכוי ה-6 אג' כהפחתה נוספת מחשבון החשמל שלו. יש לשנות את הלוגיקה הפיננסית כך שהפרמיה תיושם גם על האנרגיה שנצרכה עצמית ב-Zero Export.

הפרמיה מוגבלת ל-17 השנים הראשונות בלבד (ראו גם דיון בסעיף 3.5 לגבי ספק לגבי 17 מול 15 שנה, ושחיקת ערכה הריאלי אם אינה צמודת מדד).

🔴 רגולציה מעודכנת: חיוב עלות מערכתית (Systemic Grid Fee, 2025/2026)

החל משנת 2025/2026, חברת החשמל החלה לחייב בפועל צרכנים עסקיים ופרטיים בחיוב הנקרא "חיוב עלות מערכתית" בגין אנרגיה שהם מייצרים וצורכים ישירות מאחורי המונה. החיוב נועד לממן את שירותי הגיבוי והאיזון שהרשת הארצית (נגה וחח"י) מספקת למתקנים אלו.

אי-הכללת חיוב זה מנפחת את שווי האנרגיה בצהריים ומציגה רווחיות כוזבת. המחשבון המאוחד מנכה חיוב זה ישירות מכל קוט"ש המיוצר ונצרך עצמית, או נפרק מהסוללה.

⚠ הערת פער נתונים בין סבבי אימות: המסמכים השונים תיעדו את החיוב המערכתי בשני שלבי דיוק שונים. סבב מוקדם ("סריקה אטומית") ציין טווח ראשוני של 3–6 אגורות לקוט"ש (הטיה משוערת ~10% בחיסכון השנתי, ברירת מחדל מוצעת cfg_systemic_grid_fee = 0.04 ₪/קוט"ש). סבב מאוחר ומדויק יותר ("סריקה גרעינית" והאנציקלופדיה ההנדסית) קבע נתון מדויק של 9.09 אגורות לקוט"ש (ללא מע"מ), עם הטיה משוערת של ~15% בחיסכון השנתי. הקוד המתוקן הסופי (חלק 6, סעיף 6.3) משתמש בקבוע המדויק 0.0909. שני הנתונים נשמרים כאן כתיעוד היסטורי של תהליך האימות.

2.4 מבנה פיננסי וקפיטליסטי — מימון ו-WACC

תנאי המימון בישראל 2026

בשל סביבת הריבית הגבוהה (ריבית פריים גבוהה), עלויות המימון לפרויקטים סולאריים עומדות כיום על כ-6.5% עד 7.5% בשנה (עבור מוסדות ופרטיים בהתאמה). המחשבון משתמש בריבית זו כברירת מחדל מאומתת.

WACC (עלות ההון המשוקללת)

בעסקים גדולים, CFO ירצה להשוות את תשואת הפרויקט ל-WACC של החברה:

WACC = (E/V × Re) + (D/V × Rd × (1 - Tc))

כאשר Re הוא עלות ההון העצמי, Rd ריבית החוב, Tc מס החברות, E הון עצמי, ו-D סכום החוב. השקעה במערכת סולארית כדאית רק אם ה-Project IRR שלה גדול מה-WACC של החברה. המחשבון המאוחד מאפשר להשוות זאת ישירות.

2.5 דמוגרפיה ומגזרים — הדרישה ההלכתית (חשמל כשר)

ניתוח צורכי המגזר הדתי-חרדי והכלכלה של ביטול הגנרטורים הקהילתיים. בישראל, עשרות אלפי משפחות בבני ברק, ירושלים, אלעד ומודיעין עילית נמנעות מצריכת חשמל מהרשת בשבת מחשש לחילול שבת בתחנות הכוח. הן מחוברות לגנרטורים שכונתיים פיראטיים ויקרים במיוחד, או משלמות על מערכת מצברים ביתית פשוטה הנטענת בשישי מהרשת ונפרקת בשבת.

💰 החיסכון הכלכלי הישיר מהסוללה הביתית לשבת כשרה

גנרטור קהילתי גובה תעריף שטוח וגבוה מאוד לכל אמפר מחובר (לעיתים מעל 3.5 ₪ לקוט"ש סולר אפקטיבי). סוללה הנטענת בשישי בצהריים מהפאנלים הסולאריים (עלות ייצור אפסית) ומפרקת בשבת מייצרת חיסכון עצום:

החיסכון השנתי מגנרטור (₪) = צריכת שבת (קוט"ש) × מחיר גנרטור (₪/קוט"ש) × 52 שבתות

עבור משפחה הצורכת 20 קוט"ש בשבת, מעבר לגנרטור סולארי חוסך ₪3,640 בשנה ישירות רק על סעיף זה. המחשבון המאוחד משקלל זאת במדויק.

2.6 🧠 פיזיקה מתקדמת — מקדם טמפרטורה (הפסד החום הישראלי)

פאנלים סולאריים נבחנים במעבדה בטמפרטורה של 25°C (STC). אולם, בישראל בקיץ טמפרטורת פני התא של הפאנל מגיעה ל-65°C ומעלה. מקדם הטמפרטורה הטיפוסי של פאנל סיליקון עומד על 0.35%- לכל מעלה מעל 25°C (נכון לדגמי 2026).

📊 חישוב הפסד הטמפרטורה בפועל בקיץ הישראלי

הפסד תפוקה (%) = (65°C - 25°C) × -0.35% = -14%

השלכה: בשיא הקיץ בצהריים, למרות קרינת השמש החזקה, המתקן ייצר 14% פחות מההספק הנומינלי שלו בשל חום המכשולים המותקנים על הגג. המחשבון המאוחד לוקח זאת בחשבון במקדמי העונתיות החודשיים המשודרגים שלו.

2.7 ⚖️ רישוי וקניין בבתים משותפים (Israeli Real Estate Law)

ניתוח חסמי קניין ורישוי במיזמים סולאריים על גבי גגות משותפים בישראל. על פי חוק המקרקעין — סעיף 59ח (התקנת מתקן סולארי בבית משותף) — גג הבית המשותף (בניין דירות) שייך לכלל הדיירים באופן יחסי. התקנת מערכת סולארית פרטית של דייר בודד דורשת הליך קנייני מוגדר:

  • לשימוש משותף (קיזוז ועד בית): נדרשת הסכמה של רוב פשוט של בעלי הדירות במבנה.
  • לשימוש פרטי של דייר בודד: הדייר זכאי להתקין מערכת על הגג המשותף ללא הסכמת שאר הדיירים, אך ורק על חלק הגג היחסי המשוייך לדירתו, ובתנאי שאין דייר אחר המבקש להשתמש בשטח זה באותו זמן.

השלכה הנדסית

שטח הגג הזמין בפועל למערכת פרטית בבית משותף קטן דרסטית (מחולק במספר הדירות בבניין). יש להגביל את משתנה roofArea בהתאם למגבלה חוקית זו בשלב 1 של המחשבון.

2.8 🔌 מיקרו-תעריפים והזרמה — קיטום רשת (Noga Grid Curtailment)

ככל שנפח הייצור הסולארי בישראל גדל, חברת נגה (מנהל מערכת החשמל) נאלצת "לקטום" (להפסיק ייצור באופן יזום מרחוק) מתקנים סולאריים גדולים בימי שבת ואביב כדי למנוע קריסת תדר ברשת (Over-frequency).

ההשלכה הכלכלית

מתקנים מעל 100 קוו"ט חשופים לקטימה של כ-1% עד 3% מהתפוקה השנתית ללא פיצוי כספי. המחשבון המאוחד מנכה אחוז זה אוטומטית כמקדם שחיקה הנדסי נוסף במתקנים גדולים.

2.9 🔋 הנדסת אגירה מתקדמת — עומס פרזיטי במיזוג המצברים

סוללות ליתיום LFP חייבות לפעול בטווח טמפרטורות צר (18°C עד 25°C) כדי למנוע שחיקה כימית מואצת או סכנת בריחה תרמית (Thermal Runaway). המשמעות היא שחדר המצברים (או ארון הסוללות החיצוני) חייב להיות ממוזג 24/7 לאורך כל הקיץ הישראלי.

📊 חישוב אובדן האנרגיה במיזוג המצברים

מזגן השומר על טמפרטורה של 22°C בתוך מכולת אגירה צורך בממוצע כ-3.5% עד 5.0% מסך האנרגיה השנתית של הסוללה.

הפסד אנרגיה שנתי (קוט"ש) = הספק מזגן (kW) × 24 שעות × 180 ימי קיץ חמים
                       = 1.5kW × 24 × 180 ≈ 6,480 קוט"ש בשנה לשירות המצברים!

השלכה: אובדן אנרגיה זה (הוצאה פנימית לא רשומה) מקטין את יעילות הארביטראז'. המחשבון המאוחד מנכה אחוז זה ישירות מרווח הארביטראז' המחושב בדיספאץ'.

חלק 3אימות הנחות לפי תחום

ליבת האימות ההנדסי-פיננסי: כל הנחה גלויה או סמויה שהוטמעה בקבצי המערכת השונים (קובץ 1–4), מאומתת מול נתוני האמת של שוק האנרגיה והרגולציה הישראלית נכון לשנת 2026, על פני שמונה תחומים. ממצאים שאומתו באופן זהה במספר סבבי בדיקה נפרדים אוחדו לרשומה אחת; מקומות בהם סבבי בדיקה שונים הגיעו לנתונים שונים באותו נושא מסומנים בבירור.

3.1 צורכי הלקוח וחוויית משתמש (UX/UI & Sales Psychology)

ניתוח ההנחות ההתנהגותיות, הפסיכולוגיות והמכירתיות שעל פיהן נבנה ממשק המשתמש של המערכת.

מאומת כנכון טולטיפים להסברת מונחים טכניים

ההנחה: הלקוח לא מבין את ההבדל בין קוט"ט (kWp) לקוט"ש (kWh), וצריך תרגום למונחים פשוטים.

יישום: שימוש בטולטיפים (ⓘ Popovers) עם מנגנון ריחוף (Event Delegation) המציג את הנוסחאות הפיננסיות ומקור הנתונים ליד כל שדה קריטי — מונע מאיש המכירות צורך לזכור נוסחאות בעל פה.

אימות מציאותי: מחקרים בתחום האנרגיה מראים שחוסר הבנה של מונחים טכניים הוא חסם מכירה מרכזי. מנגנון זה הוא כלי מכירתי ממדרגה ראשונה.

מאומת כנכון "תשובה אחת מנצחת" + קוביות גדלים כמחוללי אמון משלימים

ההנחה: איש המכירות צריך "תשובה אחת מנצחת" (המלצה) ולא רק כלי חישוב — אך הצגת כל החלופות מגבירה אמון.

יישום: מנוע אופטימיזציה (Grid Search) הרץ לולאה ובוחר את גודל המערכת שממקסם את ה-IRR כהמלצה יחידה. במקביל, "קוביות גדלים" (Battery Cubes) מציגות גריד של 10–20 קוביות המייצגות גדלים שונים, כל אחת עם החיסכון השנתי שלה — במקום להציג רק את הגודל ה"מנצח".

אימות מציאותי: לקוחות רוצים "המלצת מומחה", אך הצגת כל החלופות מגבירה את האמון כי היא מראה ללקוח שהמערכת בדקה הכל וממחישה את תהליך האופטימיזציה.

אומת כנכון ומבריק פאנל השקיפות המלאה (Transparency Panel) כמחולל אמון

ההנחה: חשיפת המנגנון האלגוריתמי המלא (Details/Summary), המסביר במילים פשוטות איך חושב כל שקל ומאיזה תא באקסל נלקח כל נתון, מורידה את ספקנות לקוח הקצה ומעניקה לאיש המכירות כלי הדרכתי בשטח.

אימות מציאותי: בענף הסולארי בישראל, לקוחות עסקיים ומוסדות דת חווים חוסר אמון במחשבוני "קופסה שחורה". פירוט השלבים המדויק הוא רכיב קריטי להעלאת אחוזי הסגירה, במיוחד במגזר הדתי-מוסדי.

החלטה: שומרים ומחברים את פאנל השקיפות לרכיבי המחשבון המאוחד.

שגוי פסיכולוגית בלבול בין Project IRR ל-Equity IRR

ההנחה בקוד: המערכת מציגה את שני המדדים זה לצד זה בטבלת התוצאות (pv.irrProject ו-pv.irrEquity).

אימות מציאותי: רוב הלקוחות (שאינם מנהלי כספים) מתבלבלים כשהם רואים שני אחוזי תשואה שונים לאותה מערכת. הצגת Project IRR (שלרוב נמוך משמעותית מה-Equity IRR הממונף) עלולה להרתיע לקוחות.

תיקון נדרש: להציג כברירת מחדל רק את ה"תשואה על הכסף שלך" (Equity IRR). את ה-Project IRR יש להסתיר תחת כפתור "נתונים פיננסיים מתקדמים" או בטולטיפ.

מטעה ויזואלית "היום לדוגמה" בגרף האגירה בוחר את יום השיא

ההנחה בקוד: פונקציית renderHourlySimResults בוחרת אוטומטית את היום עם צריכת הפסגה הגבוהה ביותר בשנה להצגה בגרף הדיספאץ' (מסומן ב-⭐).

אימות מציאותי: יום השיא השנתי הוא לרוב חריג סטטיסטי (Outlier). הצגתו כ"יום לדוגמה" גורמת לסוללה להיראות כאילו אינה מספיקה (כיסוי חלקי), למרות שביום ממוצע היא מכסה 100%.

תיקון נדרש: אלגוריתם הבחירה צריך לאתר את היום שבו הצריכה קרובה ביותר לחציון צריכת הפסגה העונתית, ולא את המקסימום המוחלט.

נפסל חלקית היררכיית שלבי ה-SPA מול צריכת זיכרון ומצב

ההנחה בקוד: חלוקת הדף ל-3 שלבים באמצעות אשף (Wizard) וסנכרון הנתונים המלא ביניהם דרך localStorage מבטיחים ריצה חלקה ללא איבוד מידע.

אימות מציאותי: מעבר נתוני ה-CSV השעתיים הגולמיים (מערך של 8,760 או 17,520 אובייקטים) דרך ה-Local Storage כגוש טקסט (JSON.stringify) יוצר תקורת עיבוד כבדה ועלול לחרוג ממגבלת הזיכרון של הדפדפן (QuotaExceededError, לרוב 5MB). הדבר מוביל לתקיעות במעבר בין שלב 1 לשלב 2.

החלטת איחוד: ה-State של נתוני הגלם השעתיים יישמר אך ורק בזיכרון הריצה הפנימי של הדף (AppController.state.activeTimeSeries), ורק מטא-דאטה וסטטיסטיקות מעובדות ומכווצות (כמו peakStats) יישמרו ב-localStorage לצורך מעבר מהיר בין מסכים.

נפסל פרדיגמת חישוב חיסכון סטטיסטי מול סימולציית אגירה חיה

ההנחה בקוד: רווחיות האגירה מחושבת על בסיס ממוצעים עונתיים גולמיים מוכפלים בימי פעילות (Static Arbitrage Value).

אימות מציאותי: שיטה זו מייצרת סטיות של עד 35% בחישוב הכדאיות. היא מניחה שכל יום פסגה מנוצל במלואו, בעוד שבפועל הצריכה בימי חול משתנה, ולא תמיד יש מספיק עודפי ייצור סולאריים (או צריכת רשת) כדי להצדיק פריקה מלאה של סוללה גדולה.

החלטת איחוד: שימוש בלעדי במנוע הדיספאץ' השעתי (State Machine) המחשב SoC אמיתי לכל שעה בשנה.

אושר ליישום מערכת ה-UI/UX המלאה שסוכמה למחשבון המאוחד

  • אשף 3 שלבים (SPA Pills): ניווט ללא רענון דף. שלב 1: צריכה. שלב 2: הנדסה ואגירה. שלב 3: פיננסי ודוח.
  • באנרים דינמיים: התראה על זיהוי מונים כפולים בקובץ ה-CSV; התראה על זיהוי מונה ייצור (P0) ושאיבתו האוטומטית; באנר המציין כי קובץ ה-JSON נטען בהצלחה.
  • גרפים (Chart.js): גרף רגישות שולית (Combo Chart — חיסכון מצטבר מול תוספת שולית) וגרף התזרים המצטבר. הערה: יש להצמיד גרסה (למשל chart.js@4.4.0) ולא להשתמש ב-@latest למניעת שבירת תאימות.
  • ייצוא אקסל (ExcelJS): שימוש ב-ExcelJS (ולא SheetJS) להפקת דוחות סופיים — מאפשר מיזוג תאים פרופורציונלי, צביעת שעות פסגה/שפל, והזרקת גרפים כתמונות (Base64) לתוך האקסל.

3.2 נתוני הלקוח, קליטה ועיבוד מקדים (Data Intake & Pre-processing)

כיצד המערכת מטפלת בקלט של הלקוח ומבצעת מניפולציות הנדסיות על נתוני הגלם.

מאומת כנכון ארבע חלופות קליטת נתונים

ההנחה: לא לכל לקוח יש קובץ CSV מחברת החשמל.

יישום: המערכת תומכת ב-4 מצבי קלט, המנותבים כולם למנוע סינתזה המייצר סדרת זמנים אחידה (8,760 שעות): קובץ CSV/XLSX חח"י (מפוענח ע"י PapaParse ו-SheetJS — המדויק ביותר), קובץ JSON מטופס מכשירים, מטריצה ידנית (12 שדות: עונה × סוג יום × שעות), והערכה שנתית גסה (סה"כ קוט"ש + סוג נכס).

אימות מציאותי: לקוחות בבנייה חדשה או עסקים לפני אכלוס לא יכולים להפיק CSV — ריבוי החלופות הכרחי.

פער אינטגרציה קריטי פורמט ה-JSON המוצפן של סקר המכשירים

טופס איסוף הנתונים (Form.html v3.0) מייצא קובץ JSON מוצפן ב-AES-GCM (.json.enc) הכולל היררכיית מיקום-קטגוריה וטווחי תאריכים עבריים מורכבים — בעוד פונקציית ingestJsonApplianceData במחשבונים הקיימים מצפה לפורמט גלוי ופשוט (v1.0, מערך שעות עבודה שבועי בלבד). העלאת הקובץ הנוכחי גורמת לקריסה מיידית. פירוט מלא כולל המפתח הקשיח וקוד הפענוח הנדרש — ראו סעיף 1.1.

הנחה סבירה אך מוגבלת + הבהרת שיטה סינתזת נתונים מהערכה שנתית (IPF)

ההנחה בקוד: הערכה שנתית (למשל 15,000 קוט"ש) מתורגמת ל-8,760 שעות באמצעות אלגוריתם IPF (Iterative Proportional Fitting) לפי סוג נכס (בית/עסק).

אימות מציאותי: האלגוריתם מתמטית נכון, אך הפרופילים הסטטיים (למשל "בית פרטי = 40% בקיץ") הם הכללות — מספיק טוב להערכה ראשונית, אך יש להדגיש ללקוח שזו הערכה בלבד.

למה לא ניתן פשוט להכפיל אחוזים: אי אפשר להכפיל אחוזים בפשטות כי הממדים (עונה / פסגה-שפל / חול-שבת) תלויים זה בזה (למשל, בעונת מעבר יש פחות שעות פסגה זמינות מאשר בקיץ). הפתרון שיושם: אלגוריתם IPF המבצע 15 סבבי כיול הדדי בין הממדים עד להתכנסות, ומבטיח שסך הצריכה בעונה, בפסגה ובימי חול יתאים בדיוק לאחוזים שהוגדרו בפרופיל הנכס.

כשל חמור / נפסל חוסר טיפול ברשומות חסרות או קטועות בקובץ חח"י

ההנחה בקוד: קריאת קובץ ה-CSV (PapaParse) מניחה סדרה מושלמת ורציפה (100% Uptime של המונה), וסוכמת את הרשומות לתוך מפתח תאריך-שעה ללא בדיקת שלמות.

אימות מציאותי: מוני חברת החשמל סובלים מניתוקי תקשורת סלולרית שכיחים. קבצים רבים מכילים "חורים" של ימים שלמים ללא מדידה. אם חסר חודש (או 15 יום) בקובץ, המערכת תחשב צריכה שנתית נמוכה בכ-8%, ותציע סוללה קטנה מדי.

תיקון נדרש: הוספת מנגנון בקרת שלמות (DataCompletenessCheck) הסופר את כמות הרשומות. אם יש פחות מ-17,520 רשומות (חצי-שעתי) בשנה, יש לבצע Scaling (ניפוח פרופורציונלי) של התוצאות ל-365 ימים, או להציג אזהרה חמורה ללקוח במקום להתעלם בשקט ולעוות את המודל.

שגוי פיזיקלית המטריצה הידנית מייצרת עומס שטוח (Flat Load)

ההנחה בקוד: כאשר מזינים "4 קוט"ש לשעה בפסגה", DataNormalizer מייצר שורות זהות של 2 קוט"ש לכל חצי שעה.

אימות מציאותי: צריכה אנושית היא "קוצנית" (Spiky) — קומקום, מזגן ומכונת כביסה יוצרים פיקים של 8kW למספר דקות, גם אם הממוצע השעתי הוא 4kWh. סימולטור האגירה יניח שהממיר (למשל 5kW) מצליח לכסות את כל הצריכה, בעוד שבמציאות הפיקים יפרצו את מגבלת הממיר וימשכו חשמל יקר מהרשת.

תיקון נדרש: הוספת "מקדם תנודתיות" (Volatility Factor) של כ-15% המפחית את יעילות הכיסוי בנתונים סינתטיים.

אומת והכרחי זיהוי מונה כפול ושחזור צריכה אמיתית

ההנחה בקוד: קובץ חח"י עשוי להכיל "מוני בדיקה" המייצרים קריאות כפולות לאותה שעה — המערכת מזהה שורות עם חותמת זמן וסוג מונה זהים, ומבצעת ממוצע (לא סכום) למניעת ניפוח הצריכה ב-100%.

בנוסף, כאשר ללקוח יש מערכת סולארית קיימת (P0 > 0), קובץ חח"י מכיל מונה "דו-כיווני" ומונה "ייצור". הצריכה האמיתית של הבית משוחזרת באמצעות:

actualKwh = genKwh - exportKwh + importKwh

אימות מציאותי: מדויק והכרחי לחלוטין. ללא שחזור זה, קריאת המונה הדו-כיווני בלבד (שהיא רק ה-Import מהרשת) מציגה צריכה נמוכה כוזבת, כי הבית צרך חלק מהחשמל ישירות מהפאנלים מבלי שהרשת ראתה זאת. המערכת מזהה זאת אוטומטית ומעדכנת את שדה P0 בהתאם לשיא הייצור שנצפה כפול 2.0 (הערכה להספק AC מותקן).

3.3 מידע מציאותי ופיזיקלי-הנדסי (Physical & Engineering Data)

אימות הקבועים הפיזיקליים המגדירים את חוקי הטבע של ייצור ואחסון האנרגיה — הליבה ההנדסית של האימות.

שמרני מדי / סתירה יחס שטח גג להספק (m2PerKwp)

ההנחה בקוד: panel.m2PerKwp = 7.5 — דרושים 7.5 מ"ר לכל 1 קוו"ט (kWp) מותקן. מופיע בכל הקבצים כברירת מחדל.

אימות מציאותי: שמרני מדי לשנת 2026. פאנלים מודרניים בטכנולוגיית N-Type TOPCon או Heterojunction (HJT), בהספקים של 600W–700W ליחידה (יצרני Tier-1), משיגים כיום נצילות שטח גבוהה בהרבה. דרישת השטח האמיתית עומדת על 4.5 עד 5.5 מ"ר לקוו"ט מותקן (כולל מרווחי בטיחות, תחזוקה והתקנה). שימוש ב-7.5 מקטין מלאכותית את ההספק המקסימלי שניתן להציע ללקוח בכ-35%.

תיקון נדרש: שדה m2PerKwp הופך לקבוע עריך במסך ההגדרות המתקדמות, עם ברירת מחדל הנדסית מעודכנת של 5.5 מ"ר.

שגיאה קריטית באג ה-AC/DC: חילוק ב-1.3 שזלג ל-CAPEX ולמדרגות התעריף

ההנחה בקוד (קובץ 4): יחס DC/AC (Oversizing) הוא 1.3 — הספק הפאנלים (DC) חולק ב-1.3 כדי לקבל את הספק הממיר (AC). עד כאן תקין ומאומת כסטנדרט ההנדסי המקובל בישראל (1.3–1.4) למיקסום ניצול הממיר. אולם, ההספק המכווץ הזה (pAc) הוזן בטעות גם לחישוב עלות ההקמה ולמדרגות התעריף:

const pAc = targetKwp / 1.3;
const pvCost = pAc * inputs.capexPV; // שגיאה! עלות מחושבת לפי AC במקום DC

המציאות: עלות ההקמה (CAPEX) מתומחרת תמיד לפי הספק הפאנלים (DC). הטעות הוזילה את המערכת ב-23% באופן מלאכותי וניפחה את ה-IRR. בנוסף, pAc הוזן גם כקצב הטעינה של הסוללה (inverterPowerKw), מה שקיבע את קצב הטעינה ללא קשר לגודל הסוללה בפועל.

התיקון המיושם: עלות ההקמה מחושבת תמיד לפי DC. קצב טעינת סוללה מחושב לפי C-rate (ברירת מחדל 0.2C מקיבולת הסוללה), ללא קשר לממיר הסולארי. תוקן במפרט המאוחד.

שגוי פיזיקלית — לא מטופל הפסד קיטום (Inverter Clipping) אינו מנוכה

ההנחה הסמויה בקוד: התפוקה השנתית מחושבת כפשוט KWp * yield_base, תוך התעלמות מ"קיטום" (Clipping).

אימות מציאותי: כאשר יחס DC/AC הוא 1.3, בשעות שיא בקיץ הפאנלים ייצרו יותר ממה שהממיר מסוגל להעביר לרשת — האנרגיה העודפת "נחתכת" והולכת לאיבוד. המודל הנוכחי אופטימי מדי.

תיקון נדרש: יש להפחית כ-1.5% עד 2.5% מהתפוקה השנתית הכוללת כ"הפסד קיטום" כאשר יחס ה-DC/AC עולה על 1.25.

מדויק לחלוטין יעילות מחזור סוללה (Round-Trip Efficiency)

ההנחה בקוד: הפסד טעינה 7% (effCharge=0.93) והפסד פריקה 6% (effDischarge=0.94), נצילות כוללת (RTE) של כ-87.4%. מיושם בקבצים 2 ו-3; קובץ 4 מניח בטעות 100%.

אימות מציאותי: מדויק לחלוטין. סוללות ליתיום LFP (Lithium Iron Phosphate) בשילוב ממירי מתח היברידיים מציגות אובדן אנרגיה של כ-12%–14% בהמרה הכפולה (DC-AC-DC) — נתון פיזיקלי מדויק לשנת 2026. קבצים שהניחו יעילות 100% (כגון קובץ 4) נפסלו בשל הטיית תוצאות בלתי ריאלית.

נפסל שחיקת פאנלים ללא LID (Light-Induced Degradation)

ההנחה בקוד: שחיקה שנתית לינארית קבועה של 0.25% החל משנה 1: 1 - 0.0025 * (year - 1). בשנה הראשונה התפוקה היא 100%.

אימות מציאותי: פאנלים סולאריים חווים תופעה הנקראת LID (Light Induced Degradation) — ברגע שהם נחשפים לשמש בחודש/בשבועות הראשונים, הם מאבדים מיד כ-1.5%–2.0% מתפוקתם עקב שינויים כימיים בשכבת הסיליקון בעת החשיפה הראשונית לקרינת UV. רק לאחר מכן מתחילה שחיקה לינארית נמוכה יותר (כ-0.25%–0.4% לשנה, בהתאם לפאנל). התעלמות מ-LID מנפחת את תחזית הייצור בשנים 1–5 — המשפיעות ביותר על ה-IRR ותזרים המזומנים של ההלוואה.

תיקון נדרש: יישום מודל שחיקה דו-שלבי: year === 1 ? 0.985 : 0.985 - 0.0025 * (year - 1) (שנה 1 סופגת הפחתת LID מובנית של 1.5%, ומשנה 2 ואילך שחיקה לינארית של 0.25%/שנה).

פשטני מדי יעילות הממיר (Inverter Efficiency) אינה קבועה בפועל

ההנחה בקוד: יעילות פריקה קבועה על 94% (eff_discharge: 0.94) ללא תלות בעומס.

אימות מציאותי: עקומת היעילות של ממירים יורדת דרסטית בעומסים נמוכים (מתחת ל-10% מההספק הנומינלי). בלילות, כשהבית צורך רק 300W (מקרר וראוטר) מממיר של 10kW, היעילות צונחת ל-70%–80%. המודל הנוכחי אופטימי מדי לגבי פריקת לילה.

שגוי כימית עומק פריקה (DOD) כ"קיר בטון" שאינו משפיע על השחיקה

ההנחה בקוד: הסוללה נפרקת עד 95% DOD בכל יום שיש בו דרישה. שחיקת הסוללה (2.2%) קבועה ללא קשר לאופן השימוש.

אימות מציאותי: יש קשר אקספוננציאלי בין עומק הפריקה לאורך חיי הסוללה. פריקה יומית ל-95% תהרוג את הסוללה הרבה לפני שנה 15. מערכות ניהול (BMS) מודרניות מגבילות פריקה יומית ל-80%–85% כדי להבטיח את שנות האחריות.

תיקון נדרש: יש לשנות את ברירת המחדל של dod מ-0.95 ל-0.85 או 0.90 לכל היותר, כדי לשקף תכנון הנדסי אחראי שיעמוד בתנאי האחריות של היצרן.

שגוי פיזיקלית שחיקת הסוללה מוחלת רק על הערך הכספי, לא על הקיבולת הפיזית

ההנחה הסמויה בקוד: שחיקת סוללה (2.2%) מוחלת רק על הערך הכספי של הארביטראז' (revArb * Math.pow(1 - 0.022, year)). הקוד מניח שהקיבולת הפיזית (DOD) נשארת 95% לנצח.

אימות מציאותי: סוללות LFP מאבדות קיבולת כימית אמיתית. בשנה ה-10, הסוללה לא תוכל פיזית לאגור את אותה כמות קוט"ש. אם הלקוח בונה על הסוללה לגיבוי שבת (למשל 15 קוט"ש), בשנה ה-10 הסוללה תחזיק רק כ-12 קוט"ש והוא יחווה הפסקת חשמל בשבת — למרות שהמודל הכספי "לא ידע" על כך.

תיקון נדרש: שחיקת הסוללה חייבת להיות מוחלת על הקיבולת הפיזית (usableBat) בתוך לולאת ה-25 שנה, ולא רק על שורת הרווח הכספי.

תוקן באג היחידות בטעינת הדיספאץ' השעתי

הטעות המקורית: השוואת "תפוחים לתפוזים" — המקום הפנוי בסוללה (space) חושב ביחידות אחסון פנימיות (אחרי הפסד), בעוד יכולת הטעינה מהרשת חושבה ביחידות חיצוניות, ונלקח המינימום ביניהן ללא המרה:

const space = nominalKwh - currentSoC;       // יחידות פנימיות
const chargeAbility = inverterPowerKw * 0.5; // יחידות חיצוניות
chargedKwh = Math.min(space, chargeAbility); // שגיאה!
currentSoC += chargedKwh * effCharge;

התוצאה: הסוללה נטענה ב-93% מהפער בלבד בכל צעד, ולא הגיעה ל-100%.

התיקון: המרת ה-space ליחידות רשת חיצוניות באמצעות חילוק ביעילות הטעינה לפני ההשוואה:

const requiredGridKwhToFill = space / effCharge;
const actualGridKwhDrawn = Math.min(requiredGridKwhToFill, chargeAbility);
chargedKwh = actualGridKwhDrawn;
currentSoC += actualGridKwhDrawn * effCharge;

קצב הטעינה/פריקה עצמו אינו קבוע עוד — הוא מחושב לפי C-rate (ברירת מחדל 0.2C, טעינה מלאה ב-5 שעות) או לפי הספק ממיר שהוזן ידנית.

שגוי הנדסית קצב פריקה (C-Rate) קבוע לכל גדלי הסוללה בסימולציה

ההנחה בקוד: בסימולציות האגירה, inverterPowerKw (הקובע את קצב הפריקה המרבי) נשאר קבוע לכל 10 הגדלים הנבדקים בגריד הקוביות.

אימות מציאותי: שגוי הנדסית. מתקין לא יתקין סוללה של 80 קוט"ש עם ממיר קטן של 5 קוו"ט (זה יגביל את פריקתה לקצב זניח של 0.06C). גודל הממיר משתנה בהתאמה לנפח הסוללה.

החלטת איחוד: קצב הפריקה והטעינה השעתי בסימולציה מוגבל דינמית לכל מועמד לפי יחס של 0.2C (הספק הממיר שווה ל-20% מנפח הסוללה הנבדקת באותו צעד, עד לתקרת חיבור הרשת) — תכנון הנדסי מציאותי.

ראו גם מקדם טמפרטורה — הפסד החום הישראלי

הפסד תפוקה נוסף של כ-14% בשיא הקיץ הישראלי בשל חום פני התא (65°C+ מול 25°C תקן המעבדה) — פירוט מלא, כולל נוסחת החישוב, בסעיף 2.6.

3.4 מידע תאריכי, לוח עברי ואסטרונומיה (Dates, Zmanim & Calendars)

כיצד משתלבים לוח השנה העברי, תנועת השמש ותקנות חח"י בחישוב השעתי.

שגיאה קריטית באג השקיעה (NOAA Timezone / Equation of Time)

ההנחה בקוד: פונקציית getSunsetLocalDecimal (מנוע ה-AstroEngine, מבוסס NOAA) מחשבת את שעת השקיעה המקומית לצורך קביעת כניסת שבת והחלפת היום העברי.

אימות מציאותי: הפונקציה סובלת מבאג חמור של כיווני סימנים (signs) הפוכים בחישוב ה-Equation of Time וה-Hour Angle, ומזייפת בשעות שלמות (למשל מחזירה שקיעה בשעה 21:47 בדצמבר בישראל, במקום כ-16:40). הבעיה נובעת מטיפול שגוי באזורי זמן (UTC מול שעון ישראל). הדבר פוגם לחלוטין באמינות "שעות החשמל הכשר בשבת" בייצוא האקסל ובגרפים, וגורם לתאריך העברי לגלוש ליום הבא בשעה שגויה.

תיקון נדרש: חובה להחליף בספריית Zmanim חיצונית ואמינה (או לתקן את המתמטיקה מן היסוד), המחשבת שקיעה בדיוק של ±1.5 דקות מהלוח הרשמי בישראל.

מאומת כנכון אנומליית שעות הפסגה בחורף ובשבתות

ההנחה בקוד: שעות הפסגה בחורף (17:00–22:00) חלות גם בשבתות וחגים. בקיץ ובמעבר, שבת וחג הם שעות שפל מוחלט (ימי חול בלבד לפסגה).

אימות מציאותי: תואם במדויק את תקנות רשות החשמל בישראל. זוהי אנומליה ידועה ורשמית: בחורף, שיא הביקוש הארצי (מזגני חימום, דודים) קורה גם בשבתות בערב, ולכן הרגולטור השאיר את תמחור הפסגה בעינו. בקיץ ובמעבר, שבת היא שפל מוחלט. המחשבון המאוחד משמר התנהגות מורכבת זו במדויק.

פצצת זמן תחזוקתית רשימת חגי ישראל מקודדת קשיח

ההנחה בקוד: רשימת חגי ישראל מקודדת קשיח (Hardcoded) לשנים 2020–2030 (קובץ 1).

אימות מציאותי: למרות שזה עובד כרגע, זה דורש תחזוקה ידנית מתמשכת. קבצים 2 ו-4 מכילים מנוע אלגוריתמי (AstroEngine.isYomTov) שמחשב חגים לנצח ללא צורך בעדכון.

תיקון נדרש: יש להשתמש במנוע האלגוריתמי בלבד.

שגוי התנהגותית חול המועד מסווג כיום חול רגיל

ההנחה בקוד: פונקציית isYomTov מזהה רק ימי חג שבתון (ראש השנה, סוכות א' וכו'). ימי חול המועד מסווגים כימי חול רגילים.

אימות מציאותי: במוסדות (ישיבות, בתי ספר) ובעסקים רבים, חול המועד מתאפיין בצריכה אפסית או צריכת שבת. סיווגם כימי חול רגילים בעונת המעבר (פסח/סוכות) מעוות את ממוצעי הצריכה.

תיקון נדרש: הוספת זיהוי לימי חול המועד ב-AstroEngine, והוספת צ'קבוקס בהגדרות הלקוח: "הגדר חול המועד כימי שבתון/חופשה".

נכון רגולטורית, שגוי פיזיקלית עונות המעבר (אביב וסתיו) אינן זהות בייצור

ההנחה בקוד: חודשי מרץ–מאי ואוקטובר–נובמבר מקובצים יחד תחת season = 'transition'.

אימות מציאותי: מבחינת תעריפי חח"י זה נכון. אך מבחינת ייצור סולארי, חודש מאי (אביב, שמש חזקה, טמפ' סבירה) מייצר הרבה יותר מחודש נובמבר (סתיו, עננות, ימים קצרים). הקוד מטפל בזה נכון ב-calcYield (המשתמש במקדמים חודשיים), אך בסינתזת הנתונים (IPF) הוא מתייחס לכל עונת המעבר כבלוק אחד, מה שיוצר עיוות בפיזור הצריכה הסינתטית.

שגוי אסטרונומית עקומת הייצור השעתית קבועה (Bell Curve) ללא תלות בעונה

ההנחה הסמויה בקוד: פונקציית calcYieldSimulation מניחה עקומת ייצור קבועה בין השעות 06:00–17:00, ללא תלות בעונה.

אימות מציאותי: בישראל, בשיא הקיץ (יוני) יש ייצור סולארי משמעותי עד השעה 19:30. בחורף (דצמבר) הייצור פוסק סביב 16:30. סימולציית הדיספאץ' השעתית (שמנסה לטעון את הסוללה מהשמש) תפספס שעות ייצור יקרות בקיץ שחופפות לשעות הפסגה (17:00–19:30).

תיקון נדרש: עקומת הייצור השעתית חייבת להיות דינמית ולהיגזר משעת הזריחה/שקיעה של אותו חודש (ניתן לשאוב מ-AstroEngine המתוקן).

חוסר דיוק קל שנים מעוברות אינן מטופלות

ההנחה הסמויה בקוד: הסימולציה מניחה 8,760 שעות בשנה באופן קשיח.

אימות מציאותי: כל שנה רביעית היא שנה מעוברת (8,784 שעות). על פני 25 שנה, חסרות במודל כ-150 שעות ייצור וצריכה. ההשפעה הכלכלית זניחה (פחות מ-0.2%), אך מבחינה ארכיטקטונית, מנוע הדיספאץ' צריך להיות מודע לשנים מעוברות כדי למנוע קריסות במערכי נתונים (Arrays) המצפים לגודל קבוע.

אומת ויושם זיהום גנרטור ונירמול שבתות

הבעיה: לקוחות דתיים המפעילים גנרטור בשבת רושמים "0 צריכה" במונה חח"י. מכיוון שבחורף שבת נחשבת שעת פסגה, ה-0 הזה מעוות את חציון הפסגה החורפית כלפי מטה.

הפתרון שיושם: צ'קבוקס ignoreMissingShabbat — כאשר מסומן, המערכת מסירה את שבתות החורף ממערך הסטטיסטיקה לפני חישוב החציון. בנוסף, קיים מנגנון נירמול המשלים את השבתות החסרות לפי אחוז מוגדר מחציון ימי החול.

אימות מציאותי: רשות החשמל אכן יצרה "תעריף משלים" למתקנים המשלבים אגירה ללא מונה נפרד, כדי לתמרץ הזרמה בערב. השימוש בטבלה זו הוא הנכון רגולטורית. כאשר מריצים את הדיספאץ' השעתי (מ-CSV), התוצאה שלו דורסת את ההערכה הסטטיסטית ומועברת למודל ה-25 שנה.

שגוי רגולטורית לעתיד (2026+) התעריף המשלים לאגירה מטופל כסטטי

ההנחה בקוד: המערכת משתמשת בטבלה קבועה כדי לתמחר את פריקת הסוללה, כאשר לוגיקת הדיספאץ' פורקת באופן קשיח מ-17:00.

אימות מציאותי: התעריף המשלים נועד לתמרץ פריקה בשעות שיא הביקוש של הרשת הארצית. רשות החשמל הודיעה על כוונתה להזיז את שעות הפסגה (למשל ל-18:00–23:00) ככל שיותר סולארי נכנס לרשת (תופעת "עקומת הברווז" — Duck Curve).

תיקון נדרש: לוגיקת הדיספאץ' חייבת להיות דינמית ולקרוא את שעות הפריקה מתוך אובייקט CALC_CONSTANTS, כדי שיהיה ניתן לעדכן אותן בקלות כשהרגולציה תשתנה, מבלי לשכתב את אלגוריתם הדיספאץ' עצמו.

דורש בירור משפטי משך והצמדת הפרמיה האורבנית

ההנחה בקוד: פרמיה אורבנית — תוספת של 6 אג' לקוט"ש למשך 17 שנים (מיושם בקבצים 1, 3, 4).

אימות מציאותי: סתירה חלקית. התוספת של 6 אג' נכונה (ליישובים מעל 50,000 תושבים), אך מקורות מסוימים ב-2026 מציינים שההטבה ניתנת ל-15 שנים ולא 17 — יש לוודא נתון זה מול רשות החשמל. בנוסף, לא ברור אם ה-6 אגורות צמודות למדד המחירים לצרכן; אם לא, האינפלציה תשחק את ערכן (6 אגורות בעוד 15 שנה יהיו שוות כ-4 אגורות במונחי כוח קנייה של היום) — המודל הנוכחי אינו מהוון שחיקה זו.

לעניין הבאג המשפטי של איפוס הפרמיה במצב Zero Export, ולעניין חיוב העלות המערכתית — ראו סעיף 2.3.

3.6 מידע חוקי, מיסוי ורגולציה (Legal, Tax & Regulation)

מאומת: 18% מע"מ

ההנחה בקוד: חלק מהקבצים משתמשים ב-1.17 (17%), חלק ב-1.18.

אימות מציאותי: המע"מ בישראל עלה ל-18% החל מ-1 בינואר 2025. כל קוד המכיל 1.17 הוא שגוי ומציג עלויות CAPEX שגויות לצרכנים פרטיים — יש לעדכנו ל-1.18.

שגיאה קריטית מודל המיסוי הלינארי השגוי לאדם פרטי

ההנחה בקוד:

if (taxableIncome > 27900) tax = (taxableIncome - 27900) * 0.10;
// פטור עד 27,900 ₪, ו-10% מס על העודף בלבד — שגיאה חמורה!

המציאות (פקודת מס הכנסה, סעיף 9(13א), חוק עידוד השקעה באנרגיות מתחדשות): קיימים שני מסלולים נפרדים וקשיחים לבחירת הנישום:

  • מסלול פטור מלא (Sliding Scale): פטור מוחלט ממס עד תקרה שנתית (כ-₪27,900 ל-2025/2026). אם ההכנסה עוברת את התקרה (עד כפל התקרה — כ-₪55,800), הפטור מופחת לינארית ביחס של שקל לכל שקל עודף (הפטור "נשחק"). אם ההכנסה עוברת את כפל התקרה — אין פטור בכלל במסלול זה, ומשלמים מס שולי רגיל (המסלול קורס לחלוטין).
  • מסלול מס מופחת: תשלום של 10% מס מהשקל הראשון (לא על העודף!) על כלל ההכנסה, ללא שום פטור, עד תקרת עוסק פטור של כ-₪120,000 בשנה.

המשמעות: הנוסחה בקוד היא "הכלאה" שגויה של שני המסלולים, ותמחרה מס חסר משמעותית. ללקוח המרוויח ₪40,000 היא חישבה ₪1,210 מס, בעוד שבמסלול ה-10% האמיתי עליו לשלם ₪4,000 (פער של פי-3).

פעולה נדרשת: המחשבון חייב לחשב את שני המסלולים במקביל ולבחור אוטומטית את המסלול המשתלם והחוקי ביותר ללקוח באותה שנה. שני מימושי קוד תואמים (הבוחרים אוטומטית את המינימום בין שני המסלולים) מופיעים בחלק 6 — קוד זהב.

כשל לוגי-פיזיקלי רצפת אגירה רגולטורית "מובטחת" על ידי הסוללה

ההנחה בקוד: minInjection = kwp * 800. המערכת כופה גודל סוללה מינימלי (floorBatKwh) כדי להבטיח שהלקוח יעמוד בחובת ההזרמה לרשת.

אימות מציאותי: סוללה אינה מייצרת חשמל, היא רק אוגרת אותו. אם ללקוח יש צריכה עצמית עצומה בשעות היום (למשל מפעל), הפאנלים לא ייצרו שום עודף, הסוללה לא תיטען מהשמש, והלקוח לא יעמוד בחובת ההזרמה גם אם יתקין סוללה של 1,000 קוט"ש.

תיקון נדרש: המערכת חייבת להתריע אם annualYield - annualConsumption קטן מ-minInjection. במקרה כזה שום סוללה לא תעזור, והלקוח יאבד את התעריף הרגולטורי.

שגוי חוקית/תמחורית עלות ההקמה (CAPEX) לינארית לחלוטין

ההנחה בקוד: capex = kwp * 2400.

אימות מציאותי: בישראל, מערכות מעל 50 קוו"ט (או בשטח גג מעל 700 מ"ר) דורשות היתר בנייה מלא, אישור פיקוד העורף, ותהליכי רישוי יקרים משמעותית ממערכות פטורות מהיתר.

תיקון נדרש: הוספת "מדרגת עלות רישוי" (Fixed Cost Step) ברגע ש-kwp > 50, המוסיפה כ-15,000–25,000 ₪ ל-CAPEX בגין אגרות ויועצים.

שגוי רגולטורית מגבלת הזרמה לרשת מטופלת כבינארית

ההנחה בקוד: הקוד מניח מצב בינארי — או שמותר להזרים הכל (Zero Export = False), או שאסור להזרים כלום (Zero Export = True).

אימות מציאותי: נכון ל-2026, חברת החשמל מנפיקה לעיתים קרובות אישורי הזרמה חלקיים — למשל: "מותר להתקין 100 קוו"ט פאנלים, אך מותר להזרים לרשת מקסימום 50 קוו"ט בכל רגע נתון". המחשבון לא מסוגל לדמות מצב נפוץ זה.

תיקון נדרש: החלפת הצ'קבוקס הבינארי בשדה מספרי max_grid_injection_kw. אם הייצור עולה על מספר זה, העודף חייב ללכת לסוללה או להיקטם.

חסר תשלום קבוע (דמי רשת) ללקוחות עסקיים

ההנחה בקוד: המודל מתעלם מ"תשלום קבוע" (דמי שימוש ברשת / תשלום בעד הספק).

אימות מציאותי: לקוחות עסקיים (מתח גבוה/נמוך מסחרי) משלמים תשלום חודשי קבוע על עצם גודל החיבור (למשל 345 קוו"ט), ללא קשר לצריכה. התקנת מערכת סולארית לא מבטלת תשלום זה.

תיקון נדרש: אם המחשבון מציג "חשבון חשמל צפוי: 0 ₪" הוא מטעה לקוחות עסקיים. יש להוסיף שורת "דמי רשת קבועים" שאינה ניתנת לקיזוז ע"י ייצור סולארי.

ראו גם קניין ורישוי בבתים משותפים, קיטום רשת (נגה), טופס 4

שלושה נושאים רגולטוריים-הנדסיים נוספים — מגבלת שטח גג בבית משותף (סעיף 59ח לחוק המקרקעין), קיטום ייצור ע"י נגה במתקנים מעל 100 קוו"ט, ואיסור חיבור ללא טופס 4 — מפורטים במלואם בחלק 2 (סעיפים 2.2, 2.7, 2.8).

3.7 מידע פיננסי ומימון (Financial & Funding)

המודל המפוצל נכון יותר עלות הקמת סוללה (CAPEX Battery)

ההנחה בקוד: עלות הקמה (CAPEX): פאנלים = 2,400 ₪/קוו"ט. סוללה = 510 ₪/קוט"ש + 52,330 ₪ ממיר קבוע (קבצים 1 ו-2). קבצים 3 ו-4 משתמשים במחיר סוללה שטוח של 3,500 ₪/קוט"ש.

אימות מציאותי: המודל המפוצל נכון יותר. עלות ממיר היברידי היא הוצאה קבועה גבוהה; הוספת קוט"ש נוסף לסוללה קיימת עולה שולית מעט מאוד (רק עלות התאים). שימוש במודל שטוח (3,500) מעוות לחלוטין את כדאיות הגדלת הסוללה (הופך אותה ליקרה מדי). יש להשתמש במודל המפוצל.

3.5% ריאלי נכון יותר שיעור היוון (Discount Rate) ל-NPV

ההנחה בקוד: שיעור היוון עומד על 3.5% (קבצים 1 ו-2). קבצים 3 ו-4 משתמשים ב-5% קשיח.

אימות מציאותי: בישראל, שיעור היוון ריאלי (מנוכה אינפלציה) של 3.5%–4% לפרויקטי תשתית ארוכי טווח נחשב לסטנדרט המקובל. 5% שמרני מדי.

מדויק לחלוטין חשבונאית פיצול קרן וריבית (PPMT / IPMT) לצורך ניכוי מס

ההנחה בקוד (קובץ 3): בעת חישוב מס חברות, המערכת מפצלת את תשלום ההלוואה השנתי (PMT) לקרן וריבית, ומנכה רק את הריבית כהוצאה מוכרת.

אימות מציאותי: מדויק לחלוטין חשבונאית. על פי פקודת מס הכנסה, תשלום הקרן אינו הוצאה מוכרת (הוא החזר חוב הוני), בעוד תשלום הריבית הוא הוצאה מימונית מוכרת במלואה. גרסאות קודמות שניכו את כל החזר ההלוואה מהרווח החייב במס ביצעו עבירת מס תיאורטית וניפחו את ה-IRR. יש לשמר את לוגיקת ה-IPMT.

סטייה פיננסית תשלום ההלוואה (PMT) מחושב שנתית במקום חודשית

ההנחה בקוד: pmt(loanInt, loanYrs, loanAmount) מחושב פעם בשנה.

אימות מציאותי: הלוואות בנקאיות משולמות חודשית. חישוב PMT שנתי מתעלם מריבית דריבית (Compounding) בתוך השנה — הלקוח ישלם בפועל יותר ריבית ממה שהמודל מציג.

תיקון נדרש: יש לחשב את ה-PMT החודשי (rate/12, nper*12) ולהכפיל ב-12 כדי לקבל את תזרים המזומנים השנתי המדויק.

שגוי פיננסית לפרויקטים עתירי תשואה IRR כמדד התשואה היחיד בממונף גבוה

ההנחה בקוד: שימוש ב-Equity IRR כמדד התשואה הראשי המוצג ללקוח.

אימות מציאותי: פונקציית ה-IRR מניחה מתמטית שהלקוח משקיע מחדש (Reinvests) את כל הרווחים השנתיים באותו שיעור תשואה. כאשר הלקוח לוקח 80% מימון בנקאי, ה-Equity IRR (התשואה על ההון העצמי הקטן) קופץ לעיתים קרובות לערכים לא ריאליים (88% ואף 120%) — הנחת ה-Reinvestment הזו בלתי אפשרית בשוק ההון.

תיקון נדרש: עבור פרויקטים סולאריים, חובה להשתמש ב-MIRR (Modified Internal Rate of Return), המניח שני שיעורים ריאליים ושונים: שיעור השקעה מחדש (כ-4% — פיקדון בנקאי טיפוסי) ושיעור מימון (התואם את ריבית ההלוואה בפועל, כ-5.5%–7%). זה מוריד את התשואות המנופחות (88%) למספרים הגיוניים ואמינים יותר (כ-15%–25%), ולהציג תמיד את ה-Project IRR (התשואה ללא מינוף, ריאלית סביב 12%–18%) לצדו כדי למנוע חשד אצל מנהלי כספים. דיון מורחב ברמת CFO, כולל טבלת השוואה מספרית — ראו חלק 4, סעיף 4.6.

שגוי כלכלית עלות תפעול (OPEX) קבועה נומינלית ל-25 שנה

ההנחה הסמויה בקוד: עלות התפעול (opex) נשארת קבועה נומינלית (למשל 80 ₪/קוו"ט) למשך 25 שנה.

אימות מציאותי: תעריף ההזרמה (FIT) אכן קבוע ומוגן בחוזה מול המדינה ל-25 שנה (אינו צמוד למדד). אך עלויות התפעול (ניקיון, ביטוח, טכנאים) כן צמודות לאינפלציה. המודל מנפח את הרווח בשנים המאוחרות.

תיקון נדרש: יש להוסיף מקדם אינפלציה (למשל 2.5% שנתית) שיוחל אך ורק על שורת ה-OPEX ועלויות החלפת הציוד, ולא על ההכנסות.

דורש החלטה עסקית תעריפי התעו"ז (ערך הארביטראז') מוחזקים קבועים ל-25 שנה

ההנחה בקוד: הקוד מניח שתעריפי התעו"ז (הפער בין פסגה לשפל) נשארים קבועים ל-25 שנה, ולכן ערך הארביטראז' נשאר קבוע.

אימות מציאותי: בניגוד ל-FIT שהוא חוזי, תעריפי התעו"ז משתנים כל שנה לפי עלויות הפחם/גז של חח"י. היסטורית, מחירי החשמל עולים — ערך הסוללה (הארביטראז') צפוי לגדול עם השנים, מה שמקזז את שחיקת הקיבולת שלה.

תיקון נדרש: הוספת משתנה tou_escalation_rate (ברירת מחדל 1.5%) שיוחל על רווחי האגירה בלבד.

נכון ומדויק ביותר בלאי שנתי מקושר לערך הארביטראז' (Capacity Fade)

ההנחה בקוד (קובץ 3): ערך החיסכון השנתי מהסוללה (הארביטראז') אינו קבוע, אלא נשחק בכל שנה ב-2.2% מעריכית (batteryDegradationPct = 2.2%) כדי לשקף את ירידת קיבולת הסוללה עם השנים.

אימות מציאותי: נכון ומדויק ביותר. סוללות ליתיום LFP מאבדות קיבולת כימית בהתאם למספר מחזורי הטעינה (קצב טיפוסי של כ-2% בשנה). אי-הכללת שחיקה זו (כמו בקבצים 1 ו-4) מנפחת את ה-NPV ב-12% בחישוב ל-25 שנה. המחשבון המאוחד משמר לוגיקה זו במדויק.

שימו לב: זהו נושא שונה מהתעלמות משחיקת ה-קיבולת הפיזית עצמה (ראו סעיף 3.3) — כאן מדובר בשחיקת הערך הכספי השנתי של הארביטראז'.

כשל מסחרי עלות תפעול (OPEX) של האגירה מחושבת לפי קוו"ט פאנלים במקום נפח סוללה

ההנחה בקוד המקורי: עלות התפעול השנתית (OPEX) עם אגירה קופצת ל-250 ₪ לקוו"ט מותקן (פאנלים), לעומת 80 ₪ בסולארי בלבד.

הכשל העסקי: ה-OPEX מחושב לפי הספק הפאנלים (קוו"ט), לא לפי נפח הסוללה. לקוח המתקין מערכת פאנלים קטנה של 10 קוו"ט עם סוללה ענקית של 100 קוט"ש — ה-OPEX שלו מחושב כ-2,500 ₪ בלבד. מנגד, לקוח עם 100 קוו"ט פאנלים וסוללה קטנה של 10 קוט"ש ישלם 25,000 ₪ תפעול שנתי. עיוות מוחלט.

החלטת איחוד: חישוב ה-OPEX מפוצל הנדסית: עלות סולארית קבועה (80 ₪/קוו"ט) + עלות שירות ואחריות לסוללה המחושבת לפי נפח האגירה בפועל (30 ₪ לכל קוט"ש אגירה לשנה), המייצג את מבנה חוזי השירות האמיתי בשוק.

ראו גם עומס פרזיטי — מיזוג חדר המצברים

הפסד אנרגיה נוסף של כ-3.5%–5.0% מסך האנרגיה השנתית של הסוללה, המקטין את יעילות הארביטראז' — פירוט מלא בסעיף 2.9.

3.8 מוח עסקי ואסטרטגיית מכירות (Business Logic & Strategy)

כשל עסקי מודל ה-Zero Export הסטטי (SELF_CONSUMPTION_RATE קבוע)

ההנחה בקוד: במצב בו אסור להזרים חשמל לרשת (Zero Export), המערכת מניחה ש-40% מהייצור נצרך במקום (SELF_CONSUMPTION_RATE = 0.4), והשאר נזרק/מקוטם.

הכשל העסקי: 40% הוא קבוע סטטי. המשמעות: אם הלקוח מוסיף סוללה של 100 קוט"ש, אחוז הצריכה העצמית שלו נשאר 40% בסימולציה! זה סותר את כל המהות של מכירת סוללות ב-Zero Export (שתפקידן לאגור את העודפים כדי להעלות את הצריכה העצמית ל-80%–90%).

פעולה נדרשת: המפתחים חייבים ליצור פונקציה דינמית שבה SELF_CONSUMPTION_RATE עולה ככל שיחס (קיבולת סוללה / תפוקה יומית) גדל, במקום הקבוע הסטטי.

הברקה עסקית קיזוז ימי ארביטראז' בחורף בגין גיבוי שבת כשרה

ההנחה בקוד (קובץ 2/3): אם לקוח דורש שהסוללה תשמש לגיבוי מלא בשבת, המערכת מפחיתה את מספר ימי הארביטראז' הזמינים בחורף (מ-90 ל-כ-64 ימים בלבד).

ההיגיון העסקי: מבריק ומדויק, ומציל מבוכה. אם הסוללה חייבת להיות מלאה בשישי בצהריים כדי להחזיק את כל השבת, היא "תפוסה" ולא יכולה לבצע מחזורי קנייה/מכירה (ארביטראז' — טעינת לילה, פריקת מוצ"ש) במהלך סוף השבוע הרגיל. זה מונע הבטחות שווא ללקוח הדתי על רווחים כפולים מאותה קיבולת.

אסטרטגיית מכירה מעולה הכנסה וירטואלית מחיסכון גנרטור

ההנחה בקוד: revGenSavings = 50 * estShabbatLoad * genCost.

אימות מציאותי: תרגום של "נוחות" (ביטול גנרטור רועש ומסריח) לחיסכון תזרימי ממשי ב-₪. עוזר מאוד להצדיק את עלות הסוללה הגבוהה ללקוחות שומרי שבת.

אופטימיות יתר הלקוח מפעיל את הסוללה באופן מושלם (Perfect Foresight)

ההנחה בקוד: סימולטור הדיספאץ' יודע בדיוק כמה הלקוח יצרוך בשעת הפסגה, ופורק בדיוק את הכמות הנדרשת.

אימות מציאותי: במציאות, מערכות ניהול אנרגיה (EMS) מבוססות על תחזיות. לפעמים הסוללה תפרוק מוקדם מדי, ולפעמים תשמור רזרבה מיותרת. בנוסף, לממיר ולסוללה יש צריכה עצמית (Parasitic Load) גם כשהם בהמתנה.

תיקון נדרש: הכפלת שורת הרווח מהארביטראז' ב"מקדם מציאות" (Real World Factor) של כ-0.90 עד 0.95, כדי לא להבטיח ללקוח מקסום תיאורטי שאינו אפשרי בשטח.

אסטרטגיה טובה, מימוש חסר עלות גנרטור (2.5 ₪/קוט"ש) סטטית

ההנחה בקוד: revGenSavings = 50 * estShabbatLoad * 2.5.

אימות מציאותי: מחיר הסולר משתנה, אך חשוב מכך — הפעלת גנרטור כוללת עלויות פחת, טיפולים (החלפת שמנים) ורעש. ה-2.5 ₪ מגלם כנראה רק את עלות הדלק.

המלצה עסקית: לשנות את התווית בממשק ל-"עלות הפעלת גנרטור (כולל דלק, פחת ותחזוקה)" כדי להצדיק שימוש במספר גבוה יותר (למשל 3.5 ₪/קוט"ש), מה שיגדיל משמעותית את כדאיות הסוללה למגזר הדתי.

נפסל חוק אצבע לגודל סוללה לפי הספק ממיר (Heuristic Battery Sizing)

ההנחה בקוד (קבצים 1 ו-4 / solar-calculator-spa.html):

const pAc = pDc / 1.3;
let batteryKwh = pAc * 1.5;

אימות מציאותי: כלל אצבע זה (1.5 שעות אגירה לכל קוו"ט ממיר) היה נכון היסטורית למערכות Off-Grid קטנות בלבד. הוא שגוי הנדסית ומגביל את חופש התכנון במערכות מסחריות מחוברות רשת (תעו"ז), ובמיוחד במגזר המוסדי-דתי (שבת כשרה): לקוח בעל גג קטן (למשל בית כנסת עם גג של 50 מ"ר, המאפשר רק 9 קוו"ט פאנלים) עשוי להזדקק לסוללה עצומה של 40 קוט"ש כדי לשרוד שבת שלמה — פי כמה מעבר למה שהנוסחה הישנה הייתה מאפשרת. באופן דומה, סוללה של 150 קוט"ש למפעל שסוגר ב-17:00 היא זריקת כסף לפח, גם אם יש לו ממיר של 100 קוו"ט. גודל הסוללה חייב להיגזר אך ורק מנפח הצריכה בשעות הפסגה (או מדרישת גיבוי השבת), ללא כל תלות בהספק הפאנלים.

תיקון נדרש: מחיקת כלל האצבע הזה לחלוטין. מנוע האגירה ומנוע המערכת הסולארית מופרדים לחלוטין; גודל הסוללה ייקבע אך ורק על ידי מנוע האופטימיזציה (Grid Search) שסורק את נתוני ה-CSV ומתבסס על צריכת השבת המבוקשת או אופטימיזציית הארביטראז' (כפי שמומש בקובץ 2).

דורש תשומת לב יכולת עבודה בהפסקת חשמל (Islanding) אינה משתקפת

ההנחה בקוד: במצב הזרמה מותרת, המודל מניח ש-100% מהייצור נמכר לרשת (הסדרה תעריפית קלאסית).

אימות מציאותי: מבחינה חשבונאית זה נכון (הלקוח מזוכה על הכל). אך מבחינה פיזיקלית, החשמל נצרך קודם כל בתוך המבנה. אם הלקוח שואל "האם המערכת תעבוד בהפסקת חשמל בצהריים?" — התשובה תלויה בממיר (האם הוא Hybrid עם יכולת Islanding).

המלצה עסקית: להוסיף שדה מטא-דאטה בהצעת המחיר המציין "יכולת עבודה בהפסקת חשמל (Islanding): כן/לא", שכן זהו שיקול מכירה מרכזי שאינו משתקף ב-IRR.

מעולה "רזרבת חירום" (Buffer Kwh) באגירה הלכתית

ההנחה בקוד (קובץ 2): תכנון הסוללה לגיבוי שבת מניח רזרבה קבועה של 5% שאינה ניתנת לפריקה (reserveKwh = nominalKwh * 0.05) בנוסף לעומק הפריקה (DOD) הרגיל.

ההיגיון העסקי: מעולה. מונע מצב שבו סטייה קלה בצריכת הבית בשבת (מקרר שנפתח יותר, פלטה שחוממה מעבר לצפוי) תרוקן את הסוללה לחלוטין ותכבה את החשמל הכשר לפני צאת השבת — מה שיגרום לעוגמת נפש אדירה ללקוח.

חלק 4ניתוח פיננסי מתקדם ברמת CFO

מדריך מתודולוגי ופיננסי מקיף המיועד למנהלי כספים (CFOs), משקיעים כשירים ובעלי הון. מנתח את הכדאיות הכלכלית של השקעה במערכות פוטו-וולטאיות משולבות אגירה (PV + Storage) בישראל, בהשוואה לאפיקי השקעה אלטרנטיביים, תוך שילוב מתמטיקת המינוף, מקדמי מיסוי וניהול סיכונים חותך.

4.1 אנרגיה סולארית כנכס השקעה ריאלי (Solar as an Asset Class)

בעולם ההשקעות המודרני, מנהלי כספים מחפשים תמיד נכסים המניבים תשואה גבוהה, יציבה, בעלת קורלציה אפסית לשווקים הפיננסיים והגנה מובנית מפני אינפלציה. מערכת פוטו-וולטאית מסחרית משולבת אגירה עונה על הגדרות אלו באופן כמעט מושלם, והופכת גגות פנויים — נכס מת (Dead Asset) — ליחידת ייצור מזומנים קפיטליסטית.

🔑 שלוש התכונות שהופכות את הסולארי לנכס השקעה מועדף

  • תזרים מזומנים חוזי מובטח (Contractual Cashflow): במסלול הזרמה (FIT), המדינה מתחייבת לרכוש את החשמל המיוצר בתעריף נקוב וקבוע מראש למשך 25 שנה. אין עוד אפיק השקעה בשוק הפרטי המציע הגנה חוזית ממשלתית לטווח זמן כה ארוך.
  • הגנה אינפלציונית מובנית (Inflation Hedge): במסלולי צריכה עצמית (כולל Zero Export), שווי החשמל שנחסך צמוד ישירות ללוח התעריפים של חברת החשמל. ככל שמחירי האנרגיה עולים, החיסכון השקלי של הלקוח גדל באותו שיעור בדיוק.
  • קורלציה אפסית לשוק ההון (Zero Correlation): תנודות בבורסות העולם, משברים גיאופוליטיים או מלחמות סחר אינם משפיעים על כמות הקרינה שמספקת השמש בישראל. נכס גידור מושלם לפיזור תיקי השקעות מוסדיים ופרטיים.

💼 הטבות מס לעסקים וחברות בע"מ

4.6 אחיזת העיניים של ה-IRR והצגת מדד ה-MIRR האמיתי

מנהלי כספים מנוסים יודעים ששימוש במדד ה-IRR (תשואה פנימית) עלול להציג מצג שווא בפרויקטים המשלבים מינוף פיננסי גבוה (כגון 80% הלוואה). פונקציית ה-IRR מניחה מתמטית שכל תזרימי המזומנים החיוביים (הרווחים) שהפרויקט מייצר מדי שנה מושקעים מחדש על ידי המשקיע באותו שיעור תשואה של ה-IRR עצמו. אם ה-Equity IRR מחושב כ-88%, המודל מניח שהמשקיע מסוגל לקחת את ה-₪8,820 שקיבל בשנה הראשונה ולהשקיע אותם מחוץ לפרויקט באפיק שמניב 88% בשנה — הנחה בלתי מציאותית בשום שוק פיננסי.

כדי לתקן עיוות זה, מיושם מדד ה-MIRR (Modified Internal Rate of Return), המניח שתי ריביות ריאליות ושונות: שיעור השקעה מחדש (Reinvestment Rate) של 4.0% בשנה (תשואה ריאלית שמרנית בפיקדונות בנקאיים/אג"ח ממשלתי צמוד), ועלות המימון (Financing Rate) של 7.0% בשנה (ריבית ההלוואה בפועל).

    const inTier1 = Math.max(0, Math.min(totalP, tier1Cap) - p0);
    const inTier2 = Math.max(0, Math.min(totalP, tier2Cap) - Math.max(p0, tier1Cap));
    const inTier3 = Math.max(0, Math.min(totalP, tier3Cap) - Math.max(p0, tier2Cap));
    const inTier4 = Math.max(0, totalP - Math.max(p0, tier3Cap));

    const blendedRevenue = (inTier1 * t15) + (inTier2 * t100) + (inTier3 * t300) + (inTier4 * t630);
    let finalTariff = blendedRevenue / pAc;

    if (isUrban) {

    }

function calculateIsraelPrivateTax(income) {
    const exemptionCeiling = 27900; // תקרת פטור מעודכנת ל-2025/2026
    const flatTaxCap = 120000;      // תקרת מסלול 10% שטוח (מקביל לעוסק פטור)

    // מסלול א': פטור מופחת לינארית (Double Exemption Sliding Scale)
    let taxTrackA = 0;
    if (income <= exemptionCeiling) {
        taxTrackA = 0;
    } else {
        const excess = income - exemptionCeiling;
        const reducedExemption = Math.max(0, exemptionCeiling - excess);
        const taxableIncome = income - reducedExemption;
        taxTrackA = taxableIncome * 0.10;
    }

    // מסלול ב': 10% שטוח מהשקל הראשון (ללא שום פטור), עד תקרה
    let taxTrackB = 0;
    if (income <= flatTaxCap) {
        taxTrackB = income * 0.10;
    } else {
        // הכנסה מעל 120,000 ₪ - חייב במס שולי מלא (אין פטור ואין מס מופחת)
        taxTrackB = income * 0.35; // שיעור מס שולי משוער כברירת מחדל
    }

    // המערכת בוחרת אוטומטית את המסלול המשתלם והחוקי ביותר לנישום
    return Math.min(taxTrackA, taxTrackB);
}

6.3 סימולציית דיספאץ' שעתית מלאה (Energy Simulator) — עם תיקון יחידות וחיוב מערכתי

function runHourlyStateSimulation(series, batteryUsableKwh, inverterPowerKw) {
    const nominalKwh = batteryUsableKwh / CALC_CONSTANTS.battery.dod;
    const minSoC = nominalKwh * (1 - CALC_CONSTANTS.battery.dod);
    let currentSoC = minSoC;

    const effCharge = CALC_CONSTANTS.battery.eff_charge;    // 0.93
    const effDischarge = CALC_CONSTANTS.battery.eff_discharge; // 0.94
    const systemicFee = 0.0909; // חיוב עלות מערכתית לחח"י (₪/קוט"ש) נכון ל-2026

    let totalCharged = 0;
    let totalDischarged = 0;
    let originalCost = 0;
    let costWithBatteryAndFees = 0;

    const results = series.map(p => {
        const m = p.dateObj.getMonth() + 1;
        let peakPrice = CALC_CONSTANTS.tou.transition_peak;
        let lowPrice = CALC_CONSTANTS.tou.transition_low;

        if ([6,7,8,9].includes(m)) {
            peakPrice = CALC_CONSTANTS.tou.summer_peak;
            lowPrice = CALC_CONSTANTS.tou.summer_low;
        } else if ([12,1,2].includes(m)) {
            peakPrice = CALC_CONSTANTS.tou.winter_peak;
            lowPrice = CALC_CONSTANTS.tou.winter_low;
        }

        const currentPrice = p.isPeak ? peakPrice : lowPrice;
        let actualGridKwh = p.actualKwh;
        let chargedKwh = 0;
        let dischargedKwh = 0;

        if (!p.isPeak) {
            // טעינה בשעות שפל
            const space = nominalKwh - currentSoC;
            const chargeAbility = inverterPowerKw * 0.5; // צעדים של חצי שעה
            const requiredGridKwhToFill = space / effCharge; // תיקון באג יחידות!

            chargedKwh = Math.min(requiredGridKwhToFill, chargeAbility);
            currentSoC += chargedKwh * effCharge;
            actualGridKwh += chargedKwh;
            totalCharged += chargedKwh;
        } else {
            // פריקה בשעות פסגה
            const available = currentSoC - minSoC;
            const dischargeAbility = inverterPowerKw * 0.5;
            dischargedKwh = Math.min(p.actualKwh, available * effDischarge, dischargeAbility);
            currentSoC -= (dischargedKwh / effDischarge);
            actualGridKwh -= dischargedKwh;
            totalDischarged += dischargedKwh;
        }

        const baselineCost = p.actualKwh * currentPrice;
        // החלת עלות מערכתית (systemic fee) על קוט"ש שנצרך עצמית מהסוללה
        const systemicCharge = dischargedKwh * systemicFee;
        const newCost = (actualGridKwh * currentPrice) + systemicCharge;

        originalCost += baselineCost;
        costWithBatteryAndFees += newCost;

        return {
            dateObj: p.dateObj, actualKwh: p.actualKwh, gridKwh: actualGridKwh,
            soc: currentSoC, charged: chargedKwh, discharged: dischargedKwh, price: currentPrice
        };
    });

    return {
        results,
        annualArbitrageSavings: Math.max(0, originalCost - costWithBatteryAndFees),
        cycles: totalDischarged / batteryUsableKwh,
        coverage: (totalDischarged / series.reduce((s,p) => s + (p.isPeak ? p.actualKwh : 0), 0)) * 100
    };
}

6.4 לוח סילוקין הלוואה שנתי מדויק (פירוק PPMT/IPMT ברמת חודש)

function calculateAmortizationTable(loanAmount, annualInterestRate, years) {
    const monthlyRate = annualInterestRate / 12;
    const totalMonths = years * 12;
    const monthlyPayment = loanAmount * (monthlyRate * Math.pow(1 + monthlyRate, totalMonths)) / (Math.pow(1 + monthlyRate, totalMonths) - 1);

    let remainingPrincipal = loanAmount;
    const yearlySchedule = [];

    for (let y = 1; y <= years; y++) {
        let yearlyInterest = 0;
        let yearlyPrincipal = 0;

        for (let m = 1; m <= 12; m++) {
            const interestPayment = remainingPrincipal * monthlyRate;
            const principalPayment = monthlyPayment - interestPayment;

            yearlyInterest += interestPayment;
            yearlyPrincipal += principalPayment;
            remainingPrincipal -= principalPayment;
        }

        yearlySchedule.push({
            year: y,
            totalPayment: monthlyPayment * 12,
            principalPaid: yearlyPrincipal,
            interestPaid: yearlyInterest,
            remainingBalance: Math.max(0, remainingPrincipal)
        });
    }
    return yearlySchedule;
}

6.5 מנוע השוואת השקעות ו-MIRR ברמת CFO (Scenario Analysis)

קטע קוד JS שלם ומבודד המחשב את התזרים ומשווה את המדדים הפיננסיים (LCOE, NPV, IRR ו-MIRR) מול השקעה חלופית במדד מניות סולידי או פיקדון בנקאי:

const SolarInvestmentAnalyst = {
    // פונקציה לחישוב אנונה הלוואה חודשית והמרה לשנתית מדויקת
    calculateMonthlyLoan(amount, annualRate, years) {
        const r = annualRate / 12;
        const n = years * 12;
        if (r === 0) return (amount / n) * 12;
        const monthlyPayment = amount * (r * Math.pow(1 + r, n)) / (Math.pow(1 + r, n) - 1);
        return monthlyPayment * 12; // החזר שנתי כולל
    },

    // חישוב MIRR מדויק לפרויקט
    calculateMIRR(cashFlows, financeRate, reinvestRate) {
        const n = cashFlows.length - 1;
        let pvCosts = 0;
        let fvRevenues = 0;

        cashFlows.forEach((cf, t) => {
            if (cf < 0) {
                // מהוון עלויות לתחילת הפרויקט בריבית המימון
                pvCosts += cf / Math.pow(1 + financeRate, t);
            } else {
                // צובר רווחים לסוף הפרויקט בריבית ההשקעה מחדש
                fvRevenues += cf * Math.pow(1 + reinvestRate, n - t);
            }
        });

        if (pvCosts === 0 || fvRevenues === 0) return NaN;
        // נוסחת ה-MIRR הקנונית
        return Math.pow(Math.abs(fvRevenues) / Math.abs(pvCosts), 1 / n) - 1;
    },

    // הרצת השוואה חותכת מול S&P 500 ופיקדון בנקאי
    compareAssets(solarCapex, solarAnnualYieldKwh, tariff, inputs) {
        const loanAmount = solarCapex * inputs.loanPct;
        const equity = solarCapex - loanAmount;
        const annualLoanPMT = this.calculateMonthlyLoan(loanAmount, inputs.loanInterest, inputs.loanYears);

        // 1. תזרים מזומנים סולארי (הון עצמי ממונף)
        const solarFlows = [-equity];
        let remainingLoan = loanAmount;

        for (let y = 1; y <= 25; y++) {
            const degradationFactor = Math.max(0, 1 - 0.0025 * (y - 1)); // שחיקה לינארית מאומתת 0.25%
            const output = solarAnnualYieldKwh * degradationFactor;
            const rev = output * tariff;
            const opex = inputs.opexPv;
            const financing = y <= inputs.loanYears ? annualLoanPMT : 0;

            // חישוב ריבית לצורכי מס עסקי בלבד
            let interestPaid = 0;
            if (y <= inputs.loanYears && loanAmount > 0) {
                interestPaid = remainingLoan * inputs.loanInterest;
                const principalPaid = annualLoanPMT - interestPaid;
                remainingLoan -= principalPaid;
            }

            let tax = 0;
            if (inputs.taxStatus === 'private') {
                // הטבת מס פרטי: פטור עד 27,900 ₪, 10% מעל במסלול מופחת
                const taxable = rev - opex;
                if (taxable > 27900) tax = taxable * 0.10;
            } else {
                // הטבה עסקית: פחת מואץ 25% ל-4 שנים + ניכוי ריבית
                const depreciation = y <= 4 ? solarCapex * 0.25 : 0;
                const taxable = rev - opex - depreciation - interestPaid;
                if (taxable > 0) tax = taxable * 0.23; // מס חברות 23%
            }

            solarFlows.push(rev - opex - tax - financing);
        }

        // 2. תזרים השקעה אלטרנטיבית ב-S&P 500 (9% נומינלי, 25% מס רווחי הון בסוף)
        const sp500Flows = [-equity];
        let sp500Value = equity;
        for (let y = 1; y <= 25; y++) {
            sp500Value *= 1.09;
            sp500Flows.push(0); // ללא דיבידנדים מחולקים בתזרים השוטף
        }
        const sp500Profit = sp500Value - equity;
        sp500Flows[25] = sp500Value - (sp500Profit * 0.25);

        // 3. חישוב מדדי כדאיות משווים (MIRR בריבית השקעה מחדש של 4%)
        const solarMIRR = this.calculateMIRR(solarFlows, inputs.loanInterest, 0.04);
        const sp500MIRR = this.calculateMIRR(sp500Flows, 0, 0.04);

        return {
            equity,
            solar: {
                totalCapex: solarCapex, flows: solarFlows,
                mirr: (solarMIRR * 100).toFixed(2) + '%',
                irr: (irr(solarFlows) * 100).toFixed(2) + '%',
                cumulativeProfit: solarFlows.slice(1).reduce((s,v)=>s+v,0) - equity
            },
            sp500: {
                flows: sp500Flows,
                mirr: (sp500MIRR * 100).toFixed(2) + '%',
                cumulativeProfit: sp500Flows[25] - equity
            }
        };
    }
